# 이미지 BGA 선행 준비와 영상 디코더 수 제한 (2026-10-30)

보고서 3번의 이미지 캐시 miss/다수 영상 자산/지연 영상 따라잡기 경로를 개선했다.

## 이미지 BGA

- 플레이 시작/재시작 전에 현재·근접 이미지를 준비하고, 재생 중에는 별도 작업 스레드에서 디코딩·컬러키·확대를 수행한다. UI는 완성된 결과만 자기 캐시에 편입한다. 두 스레드가 같은 map을 수정하지 않는다.
- 앞으로 2초 이내, 최대 8개 이벤트를 선행 준비한다. 고해상도에서는 확대 캐시 수용량에 맞춰 이 개수를 줄인다. 대기 작업은 최대 8개, 완성 결과는 최대 2개다. 완성 결과 대기 예산은 64MiB이며, 기존 허용 범위의 큰 이미지 한 장은 최대 256MiB까지 허용한다.
- 기존 원본 64MiB/확대 256MiB 캐시 상한을 늘리지 않았다. 작업 중인 이미지·전달 중인 결과는 별도 메모리를 사용하므로 이 두 캐시 상한을 전체 프로세스 메모리 상한으로 해석하면 안 된다.
- 현재 필요한 이미지가 아직 없으면 UI에서 파일을 디코딩하며 기다리는 대신 직전 완성 배경을 유지하고, 완료 후 다시 합성한다. 느린 저장장치/대량 전환에서는 배경 변경이 잠시 늦을 수 있지만 음악·노트·입력 루프를 기다리게 하지 않는다.
- 4개 전체 화면 레이어가 확대 캐시를 초과할 정도로 큰 캔버스에서는 기존 동기 경로를 호환용으로 유지한다. 일반 1080p/4K는 비동기 경로다. GPU 원본 크기 텍스처 보존 방식은 이번 작업 범위 밖이다.
- 작업 스레드에는 노트/오디오 목록을 복사하지 않고 BGA 메타데이터만 전달한다. 진단 빌드의 UI 전용 perf::trace를 작업 스레드에서 기록하지 않는다.

## 영상 BGA

- 영상 ID 전체에 대해 디코더·스레드를 미리 만드는 방식에서 레이어당 현재/다음 이벤트의 최대 2개, 전체 최대 8개의 디코더로 제한했다.
- 생성·동일 이름 대체 영상 탐색·삭제는 스케줄러 스레드가 담당한다. 게임 UI의 frame()은 요청과 완성 프레임 조회만 한다. 테스트/로딩용 wait=true만 완료를 기다린다.
- 다음 영상은 1×1 출력으로 첫 프레임만 준비하며, 실제 사용 시 요청 크기로 확대한다. 원본 디코더 버퍼와 UI가 보유한 과거 프레임도 메모리를 쓰므로 전체 사용량은 파일 해상도·코덱에 따라 다르다.
- 동일 파일이라도 레이어/ID별 재생 시계는 독립적으로 유지한다. 동일 ID 재트리거, seek/재시작, POOR 시작 시각 및 기존 same-stem 대체 파일 규칙을 보존했다.
- 이후에 등장하는 깨진 영상은 그 영상이 준비 대상이 되었을 때 실패로 집계된다. 초기 로딩의 실패 수가 곡 전체의 영상 검증 결과를 뜻하지 않는다.

## 뒤처진 영상

- 비동기 디코더의 한 작업 단위를 최대 12프레임으로 나눠 새 요청·종료를 확인한다. 목표에 못 미쳤으면 UI의 추가 요청 없이도 다음 작업 단위로 계속 따라잡는다. 준비 완료 대기는 목표 프레임까지 진행한 뒤 완료된다.
- 2초 이상 뒤처지면 seek를 검토하고 같은 목표 주변에서 seek가 반복되어 진행하지 못하는 상황을 억제했다. 원래 10초 임계값을 줄였다.
- 공개된 프레임에 실제 영상 PTS와 요청 시각을 포함해 오래된 프레임 여부를 검사할 수 있게 했다. 단일 ReadSample 자체의 코덱/파일 I/O 대기까지 강제로 중단하는 구조는 아니다.

## 검증

- 비동기 이미지와 기존 동기 이미지의 전체 픽셀 비교: 확대, 알파/컬러키 레이어, 크기 변경, reset/재시작.
- 40개 영상 ID 전환 및 되감기에서 한 레이어의 디코더 2개 이하 유지, 보유 중인 프레임의 불변성.
- 4개 영상 레이어의 독립 시계와 POOR 재시작, 기존 대체 영상 규칙·취소 검사.
- 작은 디코딩 예산으로 여러 차례 처리한 뒤 목표에 도달하는지, 비동기 준비 완료가 오래된 프레임을 반환하지 않는지 검사.
- 최종 BmsGpuTests, BmsCompatibilityTests, BmsCompatibilityPlaybackTests, BmsDisplayTests, BmsBgaTests, BmsVideoTests, SevenManiaSkinApplicationTests: 7개 통과.
- 진단용 BmsPlayerProfile 컴파일도 확인했다. 중간 Display 검사에서 연습 시작 위치 키 검사 1회가 실패했으나 최신 빌드의 재검사와 최종 전체 검사는 통과했다. 해당 검사는 실제 Shift 키 상태를 참조하며, 이 실패의 원인을 별도 실험으로 확정하지는 않았다.

기본 build-rmlui-song-list/Release/BmsPlayer.exe를 갱신하고 배포 스킨의 백업/복원 해시를 확인한다. 개인 곡에 대한 FPS·RSS 개선률을 새로 측정한 작업은 아니며, 위 결과는 처리 경로·자산 수 제한 및 기능 회귀 검사다.
