# 설정 창 RmlUi 단계별 도입 계획

작성일: 2026-10-26. 단계별 계획과 진행 기록이다. 2026-10-27에 6단계까지 완료했다. 기존 Win32 설정 UI의 완전 제거는 별도 작업으로 남긴다.

진행 상태: 2026-10-26에 `main` 병합 후 `codex/rmlui-settings-ui-test` 브랜치에서 0단계를 완료했다. 항목 목록·동작 기준·재현 테스트는 [0단계 기준 보고서](RmlUiSettings-Phase0-Baseline.md)에 기록했다.

추가 진행: 같은 브랜치에서 1·2단계의 값 기반 설정 명령과 공통 런타임·입력 호스트를 구현했다. [1·2단계 구현 기록](RmlUiSettings-Phase1-2-Implementation.md)을 참고한다. 기존 설정창에서 F9로 독립 입력 실험 창을 열 수 있으며, 실제 설정 페이지의 디자인 교체와 연결은 다음 3단계다.

3단계 완료: [구현 기록](RmlUiSettings-Phase3-Implementation.md). 같은 설정 HWND 안에 새 기타 페이지를 표시하고 시스템 자원 보기부터 실제 설정·저장에 연결했다. 다른 페이지와 기타 고급 항목은 기존 네이티브 화면을 사용하며, 오류 시 기존 화면으로 복귀한다. 다음 작업은 4단계다.

## 판단

도입을 권장한다. 프로젝트는 이미 C++·RmlUi 6.3·FreeType·DX11을 사용하므로 새로운 언어 런타임 없이 곡 선택 화면과 설정 창의 색상, 여백, 버튼, 슬라이더, 글꼴을 통일할 수 있다. RML/RCSS로 배치를 관리하면 현재의 좌표 기반 컨트롤 생성 코드를 줄이기에도 적합하다.

RmlUi가 설정 저장이나 오디오·화면 모드 변경을 대신 수행하는 것은 아니다. 표시와 입력을 RmlUi로 옮기고 검증·적용·저장은 C++에 유지한다. 이번 작업에 Rust나 C# 추가 도입을 결합하지 않는다.

공식 문서는 체크박스·슬라이더·선택 목록 등의 [폼 컨트롤](https://mikke89.github.io/RmlUiDoc/pages/cpp_manual/element_packages/form.html)과 C++ 데이터에 연결하는 [데이터 바인딩](https://mikke89.github.io/RmlUiDoc/pages/data_bindings.html)을 제공한다. 실제 구현 API와 지원 스타일은 프로젝트에 고정된 `third_party/RmlUi` 6.3 소스로 확인한다. 최신 문서의 기능을 그대로 가정하지 않는다.

## 현재 코드에서 확인한 사항

| 위치 | 현재 역할과 이관 시 주의점 |
| --- | --- |
| `src/Main.cpp`: `settingsProc`, `settingsControl` | Win32 버튼·콤보박스·트랙바 생성과 설정 이벤트 처리가 모여 있다. |
| `settingsBodyProc`, `scrollSettings`, `settingsControlSubclass` | 카테고리별 표시, 스크롤, 포커스 노출을 직접 관리한다. |
| `saveDisplaySettings`, `saveKeyBindings` 및 설정 읽기 | INI 저장과 전역 상태에 연결된다. 기존 키와 값 범위를 유지해야 한다. |
| `showSettings`, `WM_CLOSE`, `WM_DESTROY` | 메인 창 비활성화, 키 캡처 취소, 미리보기 종료, 포커스 복구를 담당한다. |
| `src/RmlSongListRenderer.cpp` | 목록용 RmlUi Context·DX11·비트맵 캐시를 소유하며, RmlUi 전역 초기화와 종료까지 담당한다. 독립 렌더러 두 개를 그대로 만드는 것은 피한다. |
| `cmake/RmlSongList.cmake` | RmlUi 사용 여부와 의존성 구성이 곡 목록 옵션에 묶여 있다. 설정 창만 사용하는 조합도 분리할 필요가 있다. |

현재 카테고리는 게임플레이·그래픽·사운드·기타·요약이다. 요약 화면은 다른 페이지의 설정과 같은 값을 바꾸므로 별도 원본 상태를 만들면 안 된다. 현재 설정은 여러 항목이 즉시 적용·저장되고 닫을 때도 저장된다. 이관 도중 임의로 ‘확인 전까지 변경되지 않음’ 또는 ‘Esc로 모두 되돌림’ 정책으로 바꾸지 않는다.

곡 목록은 RmlUi로 표시하지만 선택·스크롤 입력은 ListView가 처리한다. 설정 창은 RmlUi의 실제 컨트롤을 조작해야 하므로 현재 표시 코드만 복제해서 완성할 수 없다.

## 기본 구조와 범위

기존의 별도 설정 HWND는 우선 유지하고 내부 화면을 RmlUi로 교체한다. 파일·폴더 선택기 등 Windows 기능은 기존 대화상자를 계속 호출한다. 게임 화면 내부 오버레이로 합치는 작업은 이번 범위에 넣지 않는다.

권장 연결은 다음과 같다.

`SettingsView(RML/RCSS) → SettingsController → C++ 검증·적용 함수 → 실행 상태 및 기존 INI`

`실행 상태 → SettingsSnapshot → SettingsView와 요약 페이지 동기화`

문서에 묶인 Snapshot/모델의 주소는 RmlUi 바인딩이 살아 있는 동안 유효하게 유지한다. UI 모델에 값을 넣는 것만으로 오디오나 GPU에 반영되었다고 간주하지 않는다. 실제 적용에 실패하면 UI를 실제 값으로 돌리고 이유를 표시한다.

## 0단계: 설정 목록과 기준 동작 확정

- 모든 설정의 ID, INI 섹션/키, 기본값, 허용 범위, 적용 시점, 부수 효과, 요약 화면 연결을 표로 작성한다.
- 키 재지정, 해상도·전체 화면, 오디오 버퍼, 저지연·GPU 설정, 미리보기 위치 조정 등 주의할 항목을 표시한다.
- 기존 설정 파일을 테스트 복사본으로 읽어 저장 전후 값이 유지되는 기준을 만든다. 개인 설정 파일로 테스트하지 않는다.
- 다섯 카테고리와 현재 창 크기, 키보드 조작, 설정창 닫기 후 포커스 복구를 기록한다.

완료 기준: 이관 대상 항목 누락을 판단할 수 있는 표와 기존 동작 확인 자료가 있다. 이 단계에서는 화면과 저장 동작을 바꾸지 않는다.

## 1단계: 설정 적용 로직을 HWND와 분리

- `WM_COMMAND`·`WM_HSCROLL`에 들어 있는 검증과 적용 코드를 C++ 함수로 추출한다. 기존 Win32 화면도 그 함수를 호출한다.
- 예: `setResourceUsageVisible(bool)`, `setPreviewVolume(int)`, `setFrameTarget(...)`. 구체적인 이름과 파일 구분은 0단계 결과에 맞춘다.
- 새 함수는 `HWND`에서 값을 읽지 않고 값 자체를 받는다. 적용 결과·최종 값·실패 이유를 반환한다.
- 화면 모드 변경과 렌더러 재생성 같은 작업은 UI 바인딩 콜백 안에서 바로 화면을 파괴하지 않도록 메인 스레드 명령으로 넘긴다.
- 슬라이더는 UI 표시를 바로 갱신하되 무거운 장치 재생성과 INI 쓰기는 기존 동작을 확인한 뒤 확정/드래그 종료 시점 등으로 명시한다. 예기치 않은 저장 정책 변경은 피한다.

완료 기준: 기존 설정 화면에서 동작이 유지되며, UI 없이 주요 값의 검증·적용·저장 왕복을 확인할 수 있다.

## 2단계: RmlUi 공통 수명과 설정 창 입력 호스트 구성

- 공통 `RmlUiRuntime`이 RmlUi Initialize/Shutdown, 파일·글꼴 인터페이스 수명을 소유하도록 추출한다. 곡 목록과 설정 창이 각각 전역 종료를 호출하지 않는다.
- 각 창의 Context, 문서, 렌더 타깃, 입력 포커스는 구분한다. 현재 DX11 렌더러를 공유할지 창별 렌더러로 나눌지는 고정된 6.3의 Context/RenderInterface API와 순차 렌더링 동작을 확인해 결정한다.
- 모든 RmlUi 조작은 UI 스레드에서 처리한다. 한 창의 문서/텍스처 정리가 다른 창의 자원을 끊지 않게 한다.
- Win32의 마우스 이동·클릭·드래그·휠, 키 Down/Up, 문자 입력, 포커스 상실, 캡처 해제, 크기·DPI 변경을 Context 입력에 연결한다.
- Tab/Shift+Tab, 방향키, Enter, Escape의 소유권을 정한다. 기존 `IsDialogMessageW`와 RmlUi가 같은 키를 중복 처리하지 않게 한다.
- 설정이 열린 동안에만 필요한 입력/상태 변경/애니메이션에 맞춰 다시 그린다. 기존 목록의 더블 버퍼 합성 원칙을 유지해 배경만 보이는 중간 프레임을 막는다.
- 기존 GPU→CPU 읽기 방식을 먼저 사용할 수 있으나 슬라이더 드래그 시 시간과 비용을 측정한다. 매 프레임 전체 문서를 재생성하지 않는다.
- 빌드 공통 옵션과 목록/설정 화면 옵션을 분리한다. 예를 들어 공통 `BMS_ENABLE_RMLUI`, 화면별 `BMS_ENABLE_RMLUI_SONG_LIST`, `BMS_ENABLE_RMLUI_SETTINGS`를 두고 기존 옵션과의 호환을 문서화한다.

완료 기준: 설정 테스트 문서의 버튼·체크박스·슬라이더·선택 목록을 마우스와 키보드로 조작할 수 있다. 목록을 표시한 상태에서 설정을 여러 번 열고 닫아도 목록이 고장 나지 않는다.

## 3단계: 설정 외형과 작은 페이지부터 시범 도입

- `Assets/UI/settings.rml`, `settings.rcss`를 추가한다. 카테고리 탐색, 섹션 카드, 일관된 폼 간격, 닫기 영역을 구성한다.
- 요약 페이지는 여러 시스템을 건드리므로 첫 시범 대상으로 삼지 않는다. 우선 기타 페이지의 시스템 자원 보기처럼 단순한 체크 항목부터 연결한다.
- 공통 값·명령 ID로 새 UI와 기존 로직을 연결한다. 숨긴 Win32 컨트롤을 가짜 저장소처럼 만들어 조작하지 않는다.
- 시범 단계에서 아직 옮기지 않은 페이지는 기존 Win32 본문을 사용하되 RmlUi와 겹쳐 그리지 않는다. 같은 설정 창의 페이지 교체는 단계가 끝나면 제거할 임시 장치로 한정한다.
- RmlUi 초기화/파일/문서 오류가 나면 기존 설정창을 사용할 수 있게 한다. 세션 중 오류가 나도 이미 적용된 값을 잃지 않아야 한다.

완료 기준: 새 화면에서 시스템 자원 보기를 변경하면 실제 자원 표시와 플레이 화면의 FPS·BPM·배속 표시가 함께 바뀌고, 재실행해도 값이 유지된다.

## 4단계: 일반 설정을 카테고리별로 전환

구현 기록: [4단계 일반 설정 이관](RmlUiSettings-Phase4-Implementation.md). 일반 항목과 요약 페이지를 연결하고, 아직 이관하지 않은 항목은 카테고리별 기존 설정 열기로 제공한다.

- 음량 등 단순 수치 항목 → 게임플레이 일반 항목 → 그래픽의 비민감 항목 순으로 옮긴다.
- 스크롤은 본문 영역에서 처리하고 카테고리와 닫기 영역은 고정한다. 짧은 창, 고배율 DPI, 긴 한글 라벨에서도 값과 조작 영역이 잘리지 않게 한다.
- 드롭다운이 화면 밖으로 나가지 않는지, 휠과 키보드 선택이 충돌하지 않는지 확인한다.
- 실제 연결을 마친 설정부터 요약 페이지에 노출하고 모든 페이지가 동일한 Snapshot을 읽게 한다.
- 파일/폴더 선택 대화상자를 닫았을 때 설정창으로 포커스가 돌아와야 한다.

완료 기준: 이관한 항목의 기존/새 화면에서 최종 값과 저장 결과가 같고, 원래 카테고리와 요약 표시가 서로 일치한다.

## 5단계: 키 재지정·미리보기·장치 변경 처리

구현 기록: [5단계 구현과 검증 범위](RmlUiSettings-Phase5-Implementation.md). 키 지정·기존 미리보기·장치 설정을 새 화면에서 연결했으며, 실제 장비별 전체화면/Reflex와 접근성 동등성 검증은 별도 확인 항목이다.

- 키 캡처 중에는 물리 키 입력 경로를 우선한다. 키 이름용 문자 입력이나 RmlUi 탐색 명령으로 바꾸지 않는다. Escape 취소, 키 해제 대기, 포커스 상실, 창 닫기와 중복 키 정책을 유지한다.
- IME 입력이 필요한 텍스트 필드가 있는지 먼저 확인한다. 해당 필드가 있으면 조합 문자열·확정 입력을 별도 검증하고, 없다면 범위를 불필요하게 넓히지 않는다.
- 판정선·텍스트 위치·기어 미리보기는 기존 게임 렌더러와 연결한다. 초기에는 기존 미리보기 창/오버레이를 유지하고 리사이즈·설정 종료 때 정리되는지 확인한다.
- 해상도·화면 모드·GPU·저지연·오디오 버퍼 적용은 기존 적용 순서와 오류 처리를 재사용한다. 장치나 렌더 타깃이 바뀐 뒤 UI 자원도 유효해야 한다.
- 화면 확대/고대비·키보드 전용 조작·스크린리더 필요성을 확인한다. RmlUi로 바꾸는 것만으로 Win32의 접근성 지원이 동등하게 제공된다고 가정하지 않는다.

완료 기준: 키 입력, 미리보기, 장치 변경과 취소/실패/창 닫기 후에 게임 조작과 설정 상태가 정상으로 복구된다.

## 6단계: 기본 활성화와 기존 화면 정리

완료 기록: [6단계 기본 활성화와 안정화 검사](RmlUiSettings-Phase6-Implementation.md). 사용자가 5단계 수동 테스트 완료를 확인했으며, 기본 요약 화면·설정 보존·반복 개폐·빌드 옵션 검사를 추가했다. 기존 설정창 전환은 유지한다.

- 설정 목록 전체의 연결과 사용성 검증을 마친 뒤 RmlUi 설정 화면을 기본으로 켠다.
- 안정화 동안 기존 설정 UI로 전환할 수단을 유지한다. 중복 UI 제거는 별도 정리 작업으로 수행한다.
- 현재 버전과 이전 INI 파일을 읽고 저장한 뒤 재실행하여 값 보존을 확인한다.
- 곡 선택 → 설정 → 닫기 → 플레이 → 일시정지 → 설정/복귀 동작 중 실제 허용되는 경로를 모두 확인한다. 창 재진입과 자원 수명을 점검한다.
- 옵션 ON/OFF 조합, RML/RCSS 누락, 설정창 반복 열기/닫기, 창 축소·DPI 변경, 드래그 중 포커스 상실을 검사한다.
- 화면 응답 시간·닫힌 설정창의 불필요한 렌더링·반복 개폐 시 메모리/GDI/GPU 자원 증가 여부를 측정한다. 성능 개선을 사전에 단정하지 않는다.

완료 기준: 전체 설정 표의 검증 항목을 통과하고, 곡 목록·게임 입력·기존 INI와 기능 손실 없이 연결된다.

## 예상 파일 구분

아래 이름은 새로 만들 후보이며 현재 존재하는 파일이라는 의미는 아니다.

| 후보 | 책임 |
| --- | --- |
| `SettingsState.h` | 표시용 Snapshot, 설정 ID·선택지·값 타입 |
| `SettingsController.h/.cpp` | 검증, 적용 명령, 저장과 UI 동기화 |
| `RmlUiRuntime.h/.cpp` | 공통 RmlUi 초기화·글꼴·파일 인터페이스·종료 순서 |
| `RmlSettingsHost.h/.cpp` | 설정 HWND 입력, Context/문서, 크기·DPI·렌더링과 이벤트 연결 |
| `Assets/UI/settings.rml/.rcss` | 설정 화면 구조와 디자인 |
| `tests/SettingsControllerTests.cpp` | 값 범위, 적용 실패, INI 왕복과 요약 동기화 |
| `tests/RmlSettingsHostTests.cpp` | 실제 입력·포커스·크기·반복 개폐·목록 동시 사용 |

파일을 한 번에 모두 만드는 것보다 단계별로 실제 필요한 책임만 추출한다. 다음 구현 요청이 ‘0단계’라면 목록화와 기준 동작 확인까지만 진행한다.

## 빌드와 작업 규칙

- 사용자 배포 실행 파일은 `build-rmlui-song-list/Release/BmsPlayer.exe`로 유지한다. `BmsPlayer-Settings.exe` 같은 기능별 배포 파일을 추가하지 않는다.
- 기본 빌드 명령은 `cmake -S . -B build-rmlui-song-list`와 `cmake --build build-rmlui-song-list --config Release --target BmsPlayer`다. 새 화면의 RML/RCSS도 해당 실행 파일 옆에 복사한다.
- 실행 파일이 사용 중이라 교체가 막히면 임의로 프로세스를 종료하지 않고 종료가 필요함을 알린다. 별도 이름의 실행 파일로 우회하지 않는다.
- 테스트 격리용 빌드 디렉터리와 테스트 프로그램은 사용할 수 있다. 검증 후 최종 배포 위치를 업데이트한다.
- 현재 작업 트리의 FPS·BPM·배속 표시 설정 연동 등 기존 변경은 유지한다. 이 계획을 이유로 브랜치나 설정 파일을 되돌리지 않는다.
- 중간 규모 이상의 구현 단계는 관련 빌드·검증 후 해당 변경만 커밋한다. 이 계획 작성 자체를 설정 화면 구현 완료로 간주하지 않는다.
