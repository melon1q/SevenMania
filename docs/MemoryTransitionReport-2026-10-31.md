# SevenMania 전환 반복 메모리 검사 보고서

작성: 2026-10-31 · 실제 검사: 2026-10-30 22:27:46~22:37:29 KST

## 결론과 관리 필요도

**종합 판정: ③ 이번 전환 경로에서는 누수 징후가 약하며, 당장 메모리 관리 코드를 수정할 필요가 없다.**

요청한 순서를 같은 프로세스에서 3회 반복했다. 곡 전환 300회, 채보 전환 150회, 플레이 진입 90회·퇴장 90회를 완료했고 실패는 0회였다. 캐시 정리 뒤에도 프로그램은 살아 있는 상태에서 Private Bytes가 예열 기준 **262.66MiB → 260.46MiB**로 돌아왔다. GDI 객체는 모든 퇴장 시 109개였고 음원 데이터·영상 디코더도 매번 해제됐다.

다만 퇴장 직후 메모리가 즉시 예열 수준으로 내려오지는 않았다. 퇴장 표본 최대는 521.70MiB였고 1차 반복 후 5초 대기에서도 490.81MiB였다. 이후 정상 곡 전환 중 크게 감소했고, 최종 정리 후 예열 수준으로 복귀했다. 따라서 단일 최고치나 특정 퇴장 직후 값만으로 누수라고 판정하지 않았다. 구체적으로 어느 할당기/드라이버/캐시가 반환을 늦췄는지는 이번 측정만으로 확정하지 않았다.

| 단계 | 판정 기준 | 이번 결과 |
|---|---|---|
| ① 당장 관리 필요 | 비교 가능한 유휴·정리 지점에서도 메모리/핸들이 반복마다 누적되거나, 자원 해제 실패·실행 실패가 확인됨 | 해당 근거 없음 |
| ② 당장은 아니지만 추후 문제 가능 | 안정화 지점의 증가가 남거나 캐시 상한 초과·장기 증가 추세가 관찰되어 추가 추적이 필요함 | 이번 검사에서 지속 증가나 상한 위반을 입증하지 못함. 아래 미측정 범위의 후속 확인은 필요 |
| **③ 누수 징후가 약해 현재 수정 불필요** | 반복 후 메모리가 회복되고, 객체·음원·디코더가 정상 해제되며 실행 횟수에 비례한 잔류 증가가 없음 | **이번 검사 범위의 종합 판정** |

이 등급은 프로그램 전체에 누수가 전혀 없다는 증명이 아니다. 관측한 전환 경로에 대한 수정 우선순위 판정이다.

## 검사 프로그램과 방법

`tests/MemoryTransitionTests.cpp`에서 실제 `Main.cpp`를 포함해 별도 실행 파일을 만들었다. 임의 벡터의 할당/해제로 흉내 낸 검사가 아니라 다음 실제 경로를 호출한다.

- 곡 선택: ListView 선택과 `selectSongGroupFromListRow`·`updateSelection`.
- 채보 선택: 실제 `cycleSelectedVariant`의 좌우 왕복. 끝 항목에서 순환하지 않는 앱 동작을 반영했다.
- 진입: `beginSelectedChart`를 통해 실제 파싱·비동기 로딩·음원 준비·영상/이미지 BGA·스킨 준비·WASAPI 시작.
- 퇴장: `showBrowseView`를 통해 GPU 출력·음원·BGA·텍스트 자원을 해제하고 곡 목록으로 복귀.
- PGREAT 텍스트를 실제로 출력하고 화면을 갱신했다. GPU 출력 실패로 CPU 폴백한 표본은 0개였다.

앱은 플레이 화면 하나만 열 수 있으므로 '진입 30회 → 퇴장 30회'는 **진입/퇴장 30쌍**으로 수행했다. 각 회차는 곡 선택 100회 → 채보 선택 50회 → 플레이 진입/퇴장 30쌍 순서다. 진입 대상은 4개 채보를 번갈아 사용했고, 이에 필요한 준비용 선택은 앞의 100/50회 계수와 별도다. 예열용 진입/퇴장 4쌍도 본 계수에서 제외했다.

| 조건 | 값 |
|---|---|
| 반복 | 동일 프로세스에서 전체 순서 3회 |
| 곡 선택 대기 | 600ms — 500ms 미리듣기 요청 기준을 넘김 |
| 채보 선택 대기 | 200ms |
| 실제 로딩 완료 후 플레이 대기 | 700ms |
| 퇴장 후 측정 대기 | 700ms |
| 회차 종료 후 대기 | 5초 |
| 최종 정리 | 미리듣기/배경 정지 및 미리듣기 캐시 정리 후 5초 |
| 출력 설정 | 창 모드, 1280×720 요청, 60FPS 설정, GPU 렌더링 ON, DirectComposition OFF |
| 음원 | 실제 디코딩·출력 경로 사용, 테스트 소리는 음소거 |
| 계측 | 641개 표본, 총 583.405초(약 9분 43초) |

별도 테스트 실행 폴더와 `BMS_PLAYER_CONFIG_PATH`를 사용했다. 개인 설정·기록 및 곡 원본은 수정하지 않았다. Working Set을 강제로 비우거나 프로세스 힙을 강제 압축하지 않았다. 최종 캐시 정리 값은 명시적으로 구분했다.

## 대상과 환경

- FREEDOM DiVE: `freedomdive_spi.bme`, `freedomdive_spe.bme`.
- Oekaki: `__oekaki_03h.bms`, `__oekaki_02n.bms`. 이 조합에서 영상 디코더가 실제 활성화된 표본도 확인했다.
- Windows 11 Pro `10.0.26200`, Ryzen 7 9800X3D, 논리 프로세서 16개, OS 가시 RAM 약 31.06GiB.
- 설치 GPU는 GTX 1660 Ti와 AMD Radeon Graphics였다. 실제 선택 어댑터와 GPU 전용 메모리는 이 검사에서 별도로 기록하지 않았다.
- 빌드 당시 HEAD는 `4cf37f4`이며 기존 미커밋 작업 상태도 포함한 x64 Release다. '깨끗한 해당 커밋의 결과'라고 해석하면 안 된다. 실행 파일·사용 스킨·Main.cpp·입력 채보 SHA256은 `manifest.json`에 남겼다.
- 검사 실행 파일 SHA256: `8B5DDE7784586FA83DE51BC06DB28E4108B617E8691AA17EB79480A3CEF4DBDF`.

초기 예비 실행은 테스트 프로그램이 채보 탐색을 순환 방식으로 가정해 곡 전환 100회 뒤 중단됐다. 조작을 좌우 왕복으로 수정한 뒤 **새 프로세스/새 출력 폴더에서 전체 검사를 다시 수행**했다. 아래 표는 완료된 `validated` 실행만 집계했으며 예비 실행을 합치지 않았다.

## 실측 결과

Private Bytes는 프로세스 전용 커밋 메모리, Working Set은 현재 물리 메모리에 상주한 페이지다. 아래 용량은 MiB(1,048,576바이트)다.

### 단계별 Private Bytes

| 회차 | 곡 100회: 첫값 → 마지막 | 채보 50회: 첫값 → 마지막 | 진입 표본 최대 | 퇴장 표본 범위 | 퇴장 표본 중앙값 |
|---|---:|---:|---:|---:|---:|
| 1 | 278.52 → 232.35 | 234.61 → 253.22 | 563.46 | 271.09~499.31 | 351.50 |
| 2 | 455.64 → 270.75 | 270.76 → 272.47 | 570.71 | 285.36~514.97 | 480.03 |
| 3 | 292.48 → 271.86 | 271.86 → 275.36 | 573.76 | 284.87~521.70 | 499.26 |

퇴장 중앙값은 증가했다. 이 사실을 제외하지 않았다. 그러나 각 회차의 동일한 마지막 상태와 최종 정리 지점은 아래처럼 감소했고, 곡 전환 단계에서도 큰 회복이 관측돼 이를 영구 누적 누수의 증거로 단정할 수 없다. 종료 상태·캐시 활동·해제 시점이 다른 표본을 단순히 한 직선으로 회귀해 '회당 누수량'을 산출하는 것은 부적절하다.

### 동일 상태의 회복 확인

| 지점 | Private Bytes | Working Set | 핸들 | GDI | USER | 스레드 |
|---|---:|---:|---:|---:|---:|---:|
| 예열 뒤 기준 | 262.66 | 233.59 | 1,091 | 109 | 34 | 126 |
| 1차 반복 후 5초 대기 | 490.81 | 454.27 | 1,096 | 109 | 35 | 122 |
| 2차 반복 후 5초 대기 | 325.27 | 282.52 | 1,096 | 109 | 35 | 123 |
| 3차 반복 후 5초 대기 | 291.41 | 257.61 | 1,090 | 109 | 34 | 121 |
| 미리듣기 캐시 정리 후 5초 | **260.46** | **229.05** | **1,090** | **109** | **34** | **121** |
| 앱 창·미디어 종료 후, 프로세스 반환 직전 | 127.82 | 112.86 | 556 | 28 | 4 | 8 |

최종 캐시 정리 지점은 기준보다 Private Bytes 약 **2.20MiB 감소**, Working Set 약 **4.54MiB 감소**다. 마지막 줄은 프로세스가 종료되기 전의 전역 객체·로딩된 라이브러리를 포함하므로, 남은 127.82MiB 전체를 누수라고 해석하지 않는다.

### 자원과 최고치

- 모든 퇴장 90개 표본에서 메인 음원 디코딩 데이터는 **0바이트**, BGA 영상 디코더는 **0개**였다.
- 모든 퇴장 표본의 GDI 객체는 **109개로 일정**했다. 진입 중 일시적으로 최대 126개였다.
- 퇴장 후 핸들 범위는 1,068~1,101개였고, 최종 캐시 정리 후 기준보다 1개 적었다. 스레드도 기준 126개에서 최종 121개로 감소했다.
- 샘플링된 Private Bytes 최대는 **573.76MiB**였다. 프로세스의 실제 Private Bytes 순간 최고치를 연속 수집한 값은 아니다.
- OS가 제공한 Peak Working Set 최대는 **538.88MiB**였다. 시점별 Working Set 표본 최대는 약 535.99MiB다.
- 플레이 중 관측된 메인 음원 PCM 최대는 약 **270.62MiB**, 영상 디코더 최대는 1개였다.
- 표본상 GPU 폴백 0회, 진입 시 일시정지 상태 0회, 실행 오류 0회였다.

## 해석과 후속 우선순위

1. **즉시 누수 수정은 보류한다.** 자원이 매번 해제되고 최종 메모리가 기준으로 복귀했으므로, 현재 코드를 추측으로 바꾸는 근거가 부족하다.
2. **반환 지연은 별도의 최적화 후보로 기록한다.** 특히 첫 반복 직후 약 491MiB가 5초 동안 남았지만 이후 회복됐다. 캐시/할당기 보관/드라이버 정리 지연 등의 가능성이 있으며, 이번 프로세스 카운터만으로 원인을 확정하지 않는다. 이를 줄이려면 다음에는 할당 스택과 살아 있는 블록을 추적해야 한다.
3. **등급을 ②로 올릴 조건:** 동일한 최종 정리 지점이 추가 반복에서도 계속 상승하거나, 훨씬 많은 서로 다른 곡/긴 재생에서 캐시 상한과 무관한 잔류가 확인될 때다. 작은 차이 한 번만으로 판정하지 않는다.
4. **등급을 ①로 올릴 조건:** 계속 살아 있는 음원/디코더/객체의 증가, 실제 메모리 부족·로딩 실패, 수습되지 않는 반복 증가를 재현할 때다.

미측정 범위는 수천 곡의 서로 다른 자산, 수시간 연속 실행, 4K, 다중 영상 8개 동시 활성, 곡 완주·리절트 반복, 설정/스킨 교체다. 이번 플레이 대기는 회당 700ms이므로 곡 후반의 모든 BGA 자산을 순회하는 검사가 아니다. GPU 전용 메모리 누수나 모든 네이티브 할당의 완전한 무누수를 입증하지도 않는다.

## 산출물과 재실행

- 테스트 코드: `tests/MemoryTransitionTests.cpp`
- 실행 파일: `build-rmlui-song-list/MemoryTransition/Release/BmsMemoryTransitionTests.exe`
- 실행 도구: `tools/Run-MemoryTransitions.ps1`
- 분석 도구: `tools/Analyze-MemoryTransitions.py`
- 완료 로그/641개 원시 표본/해시/요약: `build-rmlui-song-list/Validation/MemoryTransitions-2026-10-30/validated/`의 `run.log`, `samples.csv`, `manifest.json`, `summary.json`.

동일 입력으로 재실행하려면 다음과 같이 실행한다. 새 결과 폴더가 생성되며 기본 앱의 설정·기록과 분리된다.

```powershell
$m = Get-Content -LiteralPath './build-rmlui-song-list/Validation/MemoryTransitions-2026-10-30/validated/manifest.json' -Raw | ConvertFrom-Json
./tools/Run-MemoryTransitions.ps1 -Charts $m.charts -Rounds 3
# 분석: 사용 중인 Python으로 아래 명령 실행
python ./tools/Analyze-MemoryTransitions.py '<새 결과 폴더>'
```

실행 파일은 기존 빌드 설정을 사용하므로 `build-rmlui-song-list`가 구성된 환경에서 실행한다. 테스트 실행 파일·원시 출력·개인 곡은 커밋하지 않고, 테스트 코드·실행/분석 도구·이 보고서만 변경 대상으로 둔다. 제품의 메모리 관리 코드는 이번 검사에서 변경하지 않았다.
