# 이미지 HUD 실제 플레이 프레임 조사 (2026-10-31)

## 결론과 적용 범위

이미지 HUD의 합성 update 비용만으로 실제 게임의 프레임 안정성을 설명할 수 없었다. 실제 게임·오디오 시계·입력 메시지·D2D/D3D11·Present 경로로 측정했다. 이 환경에서는 이미지 HUD가 폰트 HUD보다 P99를 악화시키는 일관된 결과를 얻지 못했다. 그러나 긴 출력 제출 간격과 드문 프레임 지연은 실제로 발생했다. 이미지 HUD의 반복 리소스 준비가 그 원인이라는 증거는 없었다.

확인된 중복 작업 한 가지를 수정했다. 불투명한 기본 스킨 기어 패널 뒤에서 기존 CPU 아이콘 4개, 배속·게이지 글자를 계속 그리는 비용이다. 이 영역은 수정 전 평균 약 0.11ms였다. 패널의 실제 디코딩 결과·좌표·불투명도·클리핑을 확인해 완전한 가림을 증명한 경우에만 해당 작업을 생략한다. 반투명·부분 스킨 등은 기존 경로를 유지한다. 프레임 불균형 전체가 해결되었다는 의미는 아니다.

- 실제 원본 SHA-256: `496b196f0987ad615e4c7ab231aae846f979740a51ecaf03427223df977d83f2`.
- 렌더링 장치에서 직접 읽은 어댑터: **NVIDIA GeForce GTX 1660 Ti**, vendor 4318 / device 8578. OS의 장치 목록만으로 사용 GPU를 추정하지 않았다.
- 1920×1080, 전체 창, GPU+DirectComposition, FPS 무제한 설정, 자원 표시 OFF. 실제 오디오 전송을 유지하되 볼륨은 0이다.
- 채보: `Creamy Sugary OVERDRIVE!!!`의 `__btb_cso_7another.bme`, 30초부터 12초. 2–11초의 중앙 9초를 집계한다. 실행마다 같은 140개 입력 이벤트를 기존 키 메시지 경로로 전달한다. 실제 메시지 지연과 최종 판정은 완전히 같지 않다. 점수 계산이나 판정 규칙은 수정하지 않았다.
- 개인 설정 대신 각 실행 전용 INI·빈 라이브러리를 사용했다. 기본 스킨/개인 곡은 수정하지 않았다. 실행 파일·채보·스킨·설정·관련 소스 해시는 각 manifest에 있다.
- 측정 대상은 사용자가 이미 작업하던 미커밋 변경을 보존한 현재 소스이다. 아래의 ‘이전’은 이전 릴리즈 전체가 아니라, 같은 바이너리에서 중복 아이콘 경로를 강제한 경우다. 커밋에는 이번 작업 변경만 분리해 담는다.

## 비교 모드의 의미

`00`: 판정 font / 콤보 font, `10`: 판정 image / 콤보 font, `01`: 판정 font / 콤보 image, `11`: 둘 다 image.

1. `original`: 원본 패키지를 바이트 그대로 복사하고 모드만 변경. 원본에는 이미지 지정이 없으므로 이미지 모드는 기존 폰트를 미리 구운 아틀라스 fallback으로 작동한다.
2. `png`: 원본의 나머지 화면을 유지하고, 기존 HUD 테스트 패키지의 6개 판정·10개 숫자 PNG를 비교용 복사본에만 넣는다. 네 모드의 HUD 위치·치수는 동일하게 맞춘다.
3. `fallback`: PNG 지정 없이 같은 실험 치수 사용. 이미지 누락 시의 폰트 fallback과 비교한다.

중요한 구현 특성: 기존 엔진은 어느 한쪽만 image여도 **font인 다른 쪽을 함께 미리 아틀라스로 굽는다**. 따라서 10/01은 독립적인 이미지 선택을 검증하지만, 다른 쪽이 기존의 매번 갱신하는 폰트 경로를 그대로 실행하는 실험은 아니다. mixed 결과를 순수한 한쪽 CPU 비용이라고 해석하면 안 된다.

## 계측이 의미하는 것

`BMS_HUD_FRAME_PROBE` 전용 실행 파일에서만 계측한다. 기본 `BmsPlayer.exe`에서는 모든 계측 매크로가 제거된다. 사전 할당한 65,536개 기록 공간에 수치만 쓰며, 종료 후 기록을 끄고 오디오를 멈춘 다음 CSV를 쓴다. 측정 구간에서 프레임 로그를 파일/콘솔에 출력하지 않는다.

- `interval_ms`: 게임 갱신 시작 사이 간격. `frame_cpu_ms`: 갱신·그리기 호출 구간의 CPU 측 **경과 시간**. 스레드의 순수 CPU 실행 시간은 아니며 스케줄링 대기가 섞일 수 있다.
- HUD update, 이미지 DrawBitmap 그룹, 마스크, 애니메이션 평가, score/gauge, 기존 기어·아이콘, BGA 배경, 리소스 준비, 타깃 교체, BeginDraw/EndDraw, 복사, Present 호출 구간을 분리한다. 중첩 scope는 합산해서 총 시간으로 해석하지 않는다.
- GPU 값은 기존 비동기 timestamp/disjoint 쿼리 4개 슬롯을 사용한다. 결과 세 개가 모두 S_OK이고 disjoint가 false일 때만 채택한다. DONOTFLUSH로 조회하며 대기 루프나 추가 Flush를 넣지 않았다. **전체 draw 명령 괄호의 GPU 타임스탬프 차이**이며 HUD만의 GPU 점유율이 아니다. 최종 CopyResource/Present와 실제 모니터 출력 시간은 포함하지 않는다.
- `accepted_gap`: S_OK인 Present 제출 간격. 물리 화면 표시 간격이 아니다. 게임 내 FPS와 별도로 집계했다.
- `bitmap_switches`: HUD DrawBitmap의 bitmap 포인터 변경 횟수이다. 실제 드라이버 텍스처 바인딩이나 배치 중단 횟수를 측정한 것은 아니다. 실 드로우콜/driver batching은 PIX·GPUView로 검증하지 못했다.
- 상세 scope를 끈 boundary-only 실행도 별도로 수행했다. 계측이 완전히 공짜라는 가정은 하지 않는다.

D2D는 그리기를 배치할 수 있으므로 DrawBitmap/EndDraw의 CPU 시간만으로 GPU 실행 비용을 추정하지 않는다. 근거: [D2D EndDraw](https://learn.microsoft.com/en-us/windows/win32/api/d2d1/nf-d2d1-id2d1rendertarget-enddraw), [D3D11 Query](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ne-d3d11-d3d11_query), [GetData](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-getdata).

### 확인한 지연과 남은 원인 후보

- 이미지 10의 한 실행에서 Present 제출 간격 31.866ms가 발생했다. 해당 구간에도 갱신 44회가 진행되었고 프레임 CPU 최대는 1.536ms였다. 준비 이벤트 대기 때문에 실제 Present 호출이 거의 없었다. 이는 HUD update 정지와 구분된다. 출력 큐/DWM/드라이버 중 무엇이 최종 원인인지는 확정하지 못했다.
- 상세 scope OFF인 이미지 11에서도 한 번 **59.591ms 갱신 간격**이 있었다. 직전 CPU 구간도 59.554ms였다. 이때 텍스트 업로드·아틀라스/타깃 생성은 없었다. scope를 꺼서 정확한 하위 구간은 알 수 없으며, OS 스케줄링이라고 단정하지 않는다.
- score/gauge를 정적 값으로 만든 비교용 패키지에서는 다른 텍스트 업로드 76회를 없앴지만 P99는 대략 1.867–1.933 → 1.818–1.860ms였다. 이 정도 표본으로 전체 문제의 원인이라고 단정할 수 없다.
- 실제 paint 구간을 더 나눈 두 실행에서는 CPU 상위 1% 프레임의 배경 처리 평균이 약 0.981ms였다. 기존 hybrid CPU 배경 경로가 남아 있다. 이 작업에서는 배경이나 렌더러를 재작성하지 않았다.

## 최소 수정

기존 CPU 아이콘 구간의 평균 0.1094 / 0.1096ms, P99 0.2199 / 0.2263ms를 확인했다. 기본 스킨 패널이 완전히 덮는 영역인데도 매번 CPU PNG 합성과 GDI 텍스트·Flush를 수행했다.

로딩 때 단색 1×1 픽셀 이미지의 실제 alpha=255, native gear panel 여부, 표시/opacity/tint, source/clip/rotation/animation 조건과 각 기어 위치의 패널 범위를 검사한다. 그리기 때 실제 아이콘 사각형 전체와 contain 클립 안에 있는지를 확인한다. 증명할 수 없거나 스킨/렌더링이 실패하면 기존 경로를 유지한다. 스킨 포맷·판정·오디오·입력 규칙은 변경하지 않았다.

실제 게임 렌더 타깃의 전체 출력 픽셀을 readback해 강제 기존 경로와 비교했다. 왼쪽/중앙/오른쪽 × 4모드, **12개 조합에서 차이 0픽셀**이었다. readback은 별도 검증 실행에서만 수행했고 성능 캡처에는 포함하지 않았다.

- 정상 캡처 총 **42회 × 12초**: 탐색/상세/범위 축소 26회, 최종 전후 비교 16회. 중앙 구간의 atlas/prepare/target/readback 재발은 없었고 기록 버퍼 초과는 0이었다. 별도 pilot/실패한 실험은 이 수에 포함하지 않았다.
- 기본 `build-rmlui-song-list/Release/BmsPlayer.exe`와 진단 실행 파일, 스킨 렌더러·에디터 Release 빌드 성공.
- 기본 실행 파일을 격리 설정으로 직접 실행해 실제 창 표시를 확인하고, 종료 확인 창에 정상 종료를 요청해 exit code 0을 확인했다. 이 실행은 시작/종료 smoke이며 수동 곡 플레이 검증은 아니다.
- CTest 스킨 관련 **7/7 통과**: loader, render, binding, application, editor smoke, animation, HUD image. 이미지 누락·손상/fallback, 자릿수 전환, 반복 준비/해제, 에디터 저장/복원 등의 기존 테스트를 포함한다.
- native 패널 검증: 세 위치의 완전 가림, 범위 밖 사각형, 반투명/숨김/clip/non-native/source 지정/animation 선언 시 기존 경로 유지. result-only 부분 스킨에서도 안전하게 false를 반환하는 회귀 검증을 추가했다.
- 원본 패키지 12조합 및 PNG 비교 패키지 12조합의 전후 GPU 출력 비교 모두 **차이 0픽셀**. 이 픽셀 비교는 판정 표시를 비운 고정 시점에서 기존 아이콘 생략의 시각적 동일성을 검증하며, PGREAT 표시 자체는 HUD 이미지 테스트와 실제 재생 캡처에서 별도로 다룬다.

추가/수정 파일: `src/HudFrameProbe.h`, `tests/HudFrameProfile.cpp`, 실행/집계 Python 도구 2개, CMake 진단 target, `CompositionPresenter.h`의 조건부 계측, `Main.cpp`의 조건부 계측·중복 아이콘 guard, `SkinRenderer`/`SkinHudImages`/`SkinApplication`의 계측·안전한 가림 조회, 렌더러/애플리케이션 회귀 테스트 및 이 보고서. 스킨 JSON 규격·에디터 저장 형식은 변경하지 않았다.

## 재실행과 산출물

```powershell
cmake --build build-rmlui-song-list --config Release --target BmsHudFrameProfile
python tools/Run-HudFrameStudy.py --label my-before --asset png --legacy
python tools/Run-HudFrameStudy.py --label my-after --asset png
python tools/Run-HudFrameStudy.py --label my-pixels --asset original --cases 00 --repeats 1 --verify
python tools/Analyze-HudFrameStudy.py build-rmlui-song-list/Validation/HudFrameStudy
```

`--legacy`는 진단 실행 파일에서만 수정 전 아이콘 경로를 강제한다. 전후 비교는 같은 바이너리로 실행하며 두 번째 반복에서는 모드·전후 순서를 뒤집었다. `--boundary`는 상세 scope를 끈다. 기존 결과를 덮어쓰지 않으므로 재실행 시 새 label을 사용한다.

원시 CSV·메타데이터·격리 INI·패키지·로그·summary.json은 `build-rmlui-song-list/Validation/HudFrameStudy/`에 있다. 빌드·곡·개인 파일·이 임시 산출물은 커밋에 포함하지 않는다.

## 불확실성

이 측정은 한 PC의 짧은 실제 엔진 자동 재생이다. 장시간 수동 플레이, 여러 곡·GPU·해상도에서의 tail latency, 물리 scanout, GPUView/PIX 드라이버 타임라인, HUD만의 GPU 실행 시간은 검증하지 않았다. 반복 PNG 디코딩이나 atlas 재생성은 배제할 근거가 있지만 모든 프레임 불균형의 최종 원인을 찾은 것은 아니다. 다음 조사는 출력 큐/스케줄링 타임라인과 공통 hybrid 배경 경로를 우선해야 한다.
