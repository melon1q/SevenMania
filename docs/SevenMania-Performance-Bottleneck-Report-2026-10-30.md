# SevenMania 성능 병목 조사 및 해결 방안

작성일: 2026-10-30 · 범위: 현재 작업 트리의 정적 분석 및 기존 실험 보고서 검토
기준 HEAD: a4faa75. 커밋되지 않은 Main.cpp/TextRasterCache.h 등의 변경도 현재 상태 그대로 읽었다.

## 결론

BGA는 유력한 병목 후보다. 특히 현재 기본 빌드의 전체 화면 복사·GPU 업로드와 CPU 기반 영상 확대·레이어 합성이 개선 우선 대상이다. 그러나 현재 증상의 주원인이 BGA라고 확정할 실측은 없다. 기존 10월 24일 실험에서는 판정·콤보 텍스트 재생성이 더 강한 지연 요인이었으며, 현재도 색상 변화에 따라 텍스트 이미지가 갱신된다.

권장 순서는 **현재 빌드 계측 → 기존 하이브리드 경로 비교 → BGA 확대·합성의 GPU 이전 → 필요한 경우 하드웨어 영상 디코딩 연결**이다. 텍스트 렌더링은 별도 대조 실험으로 병행 조사한다. C++을 다른 언어로 바꾸는 것은 이 병목의 직접적인 해결책이 아니다.

이번에는 보고서만 추가했다. 소스·설정·실행 파일 변경, 새 빌드, 실행 중 프로세스 조작, 성능 실험 실행 및 커밋은 하지 않았다. 따라서 아래 개선 효과는 별도 표시한 과거 측정값 외에는 예상이며, 현재 FPS 향상을 보장하는 수치가 아니다.

## 조사 근거와 해석 범위

- 참고 채팅: [소스별 언어 전환 제안](thread://01a16ca8-ada6-7620-846b-648cea4f03ed?hostId=local). 최근 컨트롤러·폰트·스킨 변경 흐름을 확인했다. 과거 채팅의 코드 출력보다 현재 디스크의 코드를 우선했다.
- 현재 기본 빌드 설정: `build-rmlui-song-list/CMakeCache.txt:42`의 `BMS_HYBRID_RENDERER=OFF`. Release 프로젝트의 컴파일 정의에서도 해당 매크로가 없다. 이것은 생성된 빌드 설정의 확인이며, 배포 EXE의 바이너리와 소스 일치까지 검증한 것은 아니다.
- 과거 자료: `docs/frame_bottleneck_analysis.md`, `docs/frame_optimization_experiments.md`, `docs/RenderingPerformance.md`, `docs/RenderingPerformance-2026-10-16.md`.
- 새 프로파일링은 실행하지 않았다. 현재 사용하는 곡·해상도·출력 설정별 원인과 비중은 미확정이다. 과거 원시 CSV의 재분석도 하지 않았다.

## 1. 가장 먼저 비교할 부분: 화면 전체 복사·전송

현재 기본 설정에서는 `src/HybridFrame.h`의 하이브리드 분기가 비활성이다. `src/Main.cpp:2826`에서 BGA 백플레이트를 BitBlt로 복사하며, GPU 출력 경로의 `src/CompositionPresenter.h:425`에서는 UpdateSubresource로 전체 화면을 업로드한다. BGA 자체는 dirty 상태일 때만 재합성하므로, “모든 게임 프레임에서 영상을 디코딩·합성한다”는 설명은 틀리다. 문제는 배경이 그대로여도 화면 출력 단계에서 전체 화면 데이터가 다시 전달되는 구조다.

1080p BGRA 화면 한 장은 8,294,400바이트다. 실제 업로드가 초당 240회라면 단일 전송량만 약 1.99 GB/s, 400회라면 3.32 GB/s다. 4K는 각각 약 7.96/13.27 GB/s다. 이는 단순 바이트 계산이며 실제 PCIe 측정치가 아니다. CPU 복사·합성·추가 GPU 복사 비용은 포함하지 않았다. 출력 큐가 차면 present()가 업로드 전에 반환하므로 업데이트 FPS 전체를 이 계산에 그대로 대입해서도 안 된다.

해결 제안:

1. 기존 하이브리드 경로를 별도 검증 빌드에서 ON/OFF 비교한다. 이 경로는 배경 generation이 바뀔 때만 전체 배경을 업로드한다(`CompositionPresenter.h:358`).
2. 다만 기존 하이브리드도 기어와 HUD 영역을 CPU에서 복사·음영 처리하고 다시 업로드한다(`Main.cpp:2799`, `HybridFrame.h`). “스위치 하나로 완전 GPU 렌더링”이 되는 것은 아니다.
3. 후속 단계에서 배경·레인·HUD를 GPU에서 독립 합성해 CPU 영역에 배경을 다시 복사하는 작업을 줄인다.

DirectComposition 설정과 BMS_HYBRID_RENDERER 빌드 옵션은 서로 다르다. DirectComposition만 켜서 배경 보존 경로가 활성화되는 것으로 설명하면 안 된다. CPU 출력 모드에서는 GPU 업로드 대신 GDI 전송 비용을 따로 측정해야 한다.

## 2. 영상 BGA: 비동기화는 되어 있지만 CPU 픽셀 처리가 남아 있음

현재 흐름은 다음과 같다.

영상 파일 → Media Foundation RGB32 출력 → CPU 픽셀 버퍼 복사 → CPU 확대 → 최신 프레임 공유 → UI 스레드의 BGA 합성 → 화면 업로드·표시

- `src/AsyncVideoBga.h:53`: 디코딩·확대는 이미 작업 스레드에서 수행한다. 최신 프레임 하나만 유지하므로 단순히 “디코딩 스레드를 추가하자”는 제안은 중복이다.
- `src/VideoBga.h:88`: MF_SOURCE_READER_ENABLE_VIDEO_PROCESSING을 켜고 RGB32를 요구한다. Microsoft 문서는 이 옵션의 색 변환·디인터레이싱을 소프트웨어 처리이며 실시간 재생에 최적화되지 않은 경로로 설명한다. 실제 코덱 내부 구현 전체를 측정하지 않았으므로 모든 디코딩이 반드시 CPU에서만 이루어진다고 단정하지는 않는다.
- `src/VideoBga.h:37`: ReadSample 이후 연속 버퍼를 잠그고 픽셀을 별도 vector로 복사한다.
- `src/BgaRaster.h:214`: scaleVideoFrame은 원본 픽셀을 Image에 다시 복사한다. resize는 축 테이블과 임시 행 버퍼를 생성하고 CPU에서 보간한다. 원본과 출력 크기가 같아도 이 경로에 별도 무변환 fast path가 없다.
- `src/Main.cpp:2742`: 새 영상이 도착하면 UI 스레드에서 전체 백플레이트를 채우고 영상·정지 이미지를 합성한다. 여러 영상 중 하나만 갱신돼도 해당 합성 패스의 다른 활성 레이어를 함께 처리한다. 투명·컬러키 영상은 `src/VideoComposite.h`의 픽셀 반복문을 통과한다.

해결 제안:

- 작은 실험: scaleVideoFrame의 중간 원본 복사를 없애고 입력을 읽기 전용 참조로 사용한다. 크기가 같으면 보간을 생략한다. 축 테이블·작업 버퍼 재사용은 프레임 소유권을 보장한 뒤 적용한다.
- 우선 구조 개선: 원본 해상도의 프레임을 GPU에 올리고 확대, 밝기, 알파, 컬러키, 레이어 합성을 GPU에서 처리한다. 최신 프레임 ID가 바뀔 때만 해당 텍스처를 갱신한다. CPU 확대 버퍼를 표시 해상도만큼 만들 필요가 없어지는 것이 목표다.
- 후속 개선: 동일 D3D11 장치의 IMFDXGIDeviceManager를 Source Reader에 제공하고, 지원 코덱에서는 GPU surface를 유지하는 경로를 검토한다. 기존 소프트웨어 처리 옵션에 D3D_MANAGER만 추가하는 방식은 피한다. 색 변환·픽셀 형식·장치 공유 경로를 함께 설계해야 한다.
- 구형 MPEG/AVI와 지원하지 않는 코덱은 기존 CPU 경로로 복귀한다. 색 범위, 색 공간, 상하 방향, 검정 컬러키 및 premultiplied alpha의 기존 의미가 바뀌지 않아야 한다.

공식 근거: [소프트웨어 영상 처리 옵션](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-source-reader-enable-video-processing), [Source Reader의 Direct3D 장치 연결](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-source-reader-d3d-manager).

## 3. 이미지 BGA와 많은 영상 자산에서의 순간 지연·메모리

`BgaRaster::source/scaled`는 캐시 miss 시 파일 디코딩과 확대를 호출한 스레드에서 수행한다. drawBgaBackplate에서 호출되므로 새 이미지가 처음 등장하거나 캐시에서 축출됐다가 재등장하면 UI 스레드에 작업이 몰릴 수 있다. 원본 64 MiB, 확대본 256 MiB 캐시는 이미 존재한다. 1080p 전체 화면 확대본 약 32장, 4K 약 8장 수준이며 실제 개수는 이미지 크기·변형에 따라 달라진다.

단순 캐시 상한 확대보다 앞으로 등장할 이미지의 제한된 선행 디코딩, 원본 크기 GPU 텍스처 보존, 재사용 빈도·시간 기반 캐시를 우선 검토한다. 기존 캐시는 스레드 안전 구조가 아니므로 작업 스레드에서 같은 map을 직접 수정하지 않고 완성된 결과만 넘겨야 한다.

`BgaVideoLayers::prepare`는 레이어/영상 ID마다 AsyncVideoBga를 생성하고 첫 프레임을 기다린다. 많은 영상이 선언된 곡은 reader·프레임·대기 스레드를 다수 보유할 수 있고 초기 준비도 순차적이다. 비활성 영상이 계속 디코딩된다고 볼 근거는 없지만 메모리와 로딩 시간 후보는 된다. 활성 영상과 가까운 다음 이벤트만 준비하는 제한된 풀을 검토하되, 동일 영상의 다른 시작 시각 및 반복 이벤트를 합쳐 버리지 않아야 한다.

또한 `VideoBga::update`는 한 요청에서 최대 240번 전진 처리하며, 일반 재생에서 10초를 넘는 뒤처짐에 seek한다. 수초 뒤처진 영상을 따라잡는 동안 다음 요청을 늦게 확인할 수 있다. 디코딩된 PTS와 목표 시각의 차이를 측정한 뒤 지연 프레임 건너뛰기·seek 정책을 조정한다. 프레임 개수만 줄이면 영상이 계속 뒤처질 수 있다.

## 4. BGA 외의 강한 후보: 판정·콤보 텍스트

10월 24일 기존 보고서에서는 특정 두 곡 구간의 판정 글자 캐시 miss가 처리 시간과 강하게 연관됐다. 텍스트 결합 실험의 표준 조건 P99는 2.379 → 1.918ms였지만 실제 표시·입력 지연까지 개선된 최종 배포 승자는 확정하지 못했다고 명시돼 있다. 이는 과거 결과이며 현재 스킨·폰트·빌드의 측정값이 아니다.

현재 `src/skin/SkinRenderer.cpp:93`은 PGREAT 색상 phase가 바뀌면 텍스트를 다시 준비한다. `src/HudTextStyle.h:26`의 phase는 24ms 단위다. 콤보 변경 또한 별도 글자 이미지를 요구하며 생성한 비트맵은 GPU에 업로드된다. 현재 작업 트리의 TextRasterCache에는 preoutlined 후처리 생략과 작업 DC 재사용 계열 변경이 이미 보이므로, 과거 패치를 통째로 다시 적용하자는 제안은 부적절하다.

후속 후보는 글자 모양과 색상 처리를 분리하는 것이다. 외곽선과 글리프 마스크를 캐시하고 PGREAT 색상은 GPU에서 입히며 숫자는 glyph atlas로 조합한다. 기존 이중 외곽선·글자 간격·확대 효과를 픽셀 또는 허용 오차 비교로 검증한다. 이 후보는 BGA와 독립적으로 비교해야 한다.

추가로 과거 GdiFlush의 54.183ms 단발 지연 기록이 있다. 현재도 BGA 합성·CPU 픽셀 접근 경계에 GdiFlush가 있다. 소유권·실행 순서를 확인하지 않고 이를 삭제하면 화면 손상 위험이 있다. 긴 지연이 재현될 때 ETW로 드라이버 대기와 스레드 선점을 구분한다. 현재 코드는 지뢰 목록도 매 업데이트 전체 순회하므로 지뢰가 많은 곡에 한해서는 커서 기반 탐색을 추가 후보로 둔다.

## 5. 계측에서 반드시 고쳐 읽어야 할 항목

- `video_ms`는 Main.cpp에서 gVideoBga.update 요청을 보내는 시간이다. 작업 스레드의 실제 ReadSample·확대 시간은 아니다.
- `decode_ms`는 BgaRaster::source의 이미지 경로 계측이다. 영상 디코딩 전체를 나타내지 않는다.
- `gpu_draw_ms`, `upload_ms`, `gpu_queue_ms`의 scope 값은 CPU API 소요 시간이다. GPU 실행 시간이나 모니터에 표시된 시각과 동일하지 않다.
- 부모·자식 scope가 중첩되므로 bga_ms, image_ms, backplate_build_ms를 모두 합산해서 전체 시간을 계산하지 않는다.
- 기존 Trace는 65,536행 상한이다. 400Hz에서 약 164초, 1500Hz에서 약 44초 분량이므로 긴 실험은 구간 분할 또는 수집 구조 보완이 필요하다.

추가할 진단값: 영상별 decode/scale 시간, 요청·완료 수, 목표 시각/표시 PTS/영상 나이, 프레임 drop, 이미지 캐시 miss·축출 수, 합성 횟수·시간, 실제 업로드 바이트, 스킨 글자 생성·업로드 시간, 실제 선택 GPU와 Present 성공/지연 수. 작업 스레드는 자체 카운터 또는 안전한 큐를 사용한다. 현재 UI용 perf::trace에 직접 동시에 기록하지 않는다.

## 6. 구현 전 검증 계획과 채택 기준

동일 EXE·곡·스킨·해상도·입력 replay·오디오 버퍼를 고정하고 3회 이상 순서를 바꿔 반복한다. 정지 이미지가 많은 곡, 단일 영상, 다중 영상/컬러키, 고해상도 영상, 빈번한 POOR, PGREAT·콤보가 많은 구간을 포함한다. 시작·seek·재시작 구간과 충분히 준비된 연속 재생 구간을 따로 기록한다.

| 비교 | 분리하려는 원인 |
|---|---|
| 현재 빌드 / 하이브리드 | 전체 화면 복사·업로드 비용 |
| 영상 정상 / 진단용 고정 프레임 | 영상 갱신에 따른 디코딩·합성 비용 |
| CPU 확대 / GPU 확대 | 해상도에 비례하는 확대·메모리 비용 |
| 텍스트 정상 / 진단용 동일 글자·색 고정 | 콤보·PGREAT 래스터 생성 비용 |
| 1080p / 더 낮은 해상도, 240 / 400 / 무제한 | 픽셀 수·출력 횟수 의존성 |

BGA 밝기 0만으로 영상 디코딩 OFF 대조라고 부르면 안 된다. 비하이브리드 fallback 영상은 밝기 0에도 update/request가 계속 호출된다. 고정 프레임/디코더 정지 대조는 향후 검증 전용 분기로 명확히 구분해야 한다. 이번에는 그런 코드를 추가하지 않았다.

평균 FPS뿐 아니라 update 및 실제 표시 간격의 P95/P99/P99.9, 목표 시간 초과율, 영상 PTS 지연, 입력 처리 지연, 오디오 underrun, 메모리 최대치를 비교한다. 240Hz 예산은 4.17ms, 400Hz는 2.5ms이며 이 값은 CPU 작업만의 목표가 아니라 출력 주기와 함께 해석한다. 필요시 PresentMon/ETW로 실제 출력·GPU 대기를 확인한다.

채택 조건은 반복 측정에서 긴 프레임이 줄고, 입력·오디오·영상 동기화가 악화하지 않으며, 재시작/seek/POOR·동일 영상 재트리거·알파/컬러키·기어 이동·해상도 변경·장치 손실 회귀 검증을 통과하는 것이다. FPS만 상승하고 영상이 오래된 프레임을 표시하는 변경은 채택하지 않는다.

## 실행 순서 제안

1. 현재 빌드와 사용자 증상을 재현할 기준 로그 확보. 계측 누락을 보완하고 BGA/텍스트 대조.
2. 기존 하이브리드 경로의 현재 스킨 호환성과 출력 안정성 검증. 합격 시 기본 적용 검토.
3. BGA 원본 크기 텍스처·GPU 확대·레이어 합성 도입. CPU 경로는 호환용으로 유지.
4. 영상 worker가 여전히 병목일 때 D3D11 하드웨어 디코딩 연결. 이미지 선행 로딩과 영상 풀은 해당 곡에서 측정된 문제에 따라 적용.
5. 판정 텍스트의 마스크/색상 분리 최적화를 독립 검증 후 통합.

BGA·오디오·판정 엔진은 C++을 유지하고 필요시 HLSL로 픽셀 연산을 GPU에 옮기는 방향이 적합하다. Rust/C# 전환만으로 현재의 전체 화면 복사·CPU 확대 구조가 없어지지 않으며, 이번 문제는 언어보다 처리 위치·갱신 빈도·버퍼 소유권을 바꾸는 쪽에 해결 가능성이 높다.
