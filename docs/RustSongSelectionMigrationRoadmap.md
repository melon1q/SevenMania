# Rust 곡 선택 모델 보수적 이전 로드맵

## 목적

곡 선택 기능의 데이터 처리와 선택 상태를 단계적으로 Rust로 옮겨 메모리 안전성을 높인다. 기존 C++ 플레이어, BMS 해석기, 오디오 미리 듣기, Win32 입력과 화면 렌더링은 초기 이전 범위에 포함하지 않는다. 각 단계에서 기존 C++ 경로로 되돌릴 수 있어야 한다.

Rust는 가비지 컬렉터 없이 소유권과 수명 규칙을 컴파일 시점에 검사하므로 해제 누락, 잘못된 참조, 이중 해제 같은 오류를 크게 줄일 수 있다. 다만 메모리 누수를 완전히 막지는 않는다. 참조 순환, 의도적인 메모리 보존, FFI의 잘못된 포인터 계약 등은 여전히 검토해야 한다.

## 현재 구조

- 저장소는 CMake 기반 C++20 프로젝트다. 현재 `CMakeLists.txt`는 C++ 언어만 활성화하고 `bms_song_selection` 정적 라이브러리로 `src/SongSelection.cpp`를 빌드한다.
- `src/SongSelection.h`와 `src/SongSelection.cpp`의 `SongSelectionModel`이 곡 그룹, 정렬 방향, 선택된 그룹과 채보 변형을 관리한다.
- 모델은 `Chart`, `SongGrouping.h`, `ChartOrdering.h`, `PreviewTiming.h`와 결합되어 있다. 특히 제목 정규화, 폴더 기준 그룹화, 레벨 순서, 미리 듣기 채보 선택, 한국어·일본어 정렬 결과가 기존 동작의 일부다.
- `src/Main.cpp`는 전역 `gSongSelection`을 참조한다. Win32 ListView의 입력, GDI로 그리는 `drawBrowseScreen`, 미리 듣기와 플레이 시작 연결도 이 파일에 남아 있다.
- 곡 선택 모델과 별개로, `rust/bms_backend`에 opt-in Rust 보조 backend가 있다. `BMS_USE_RUST_BACKEND`는 기본값이 `OFF`이고, Windows x64 MSVC의 Release 구성에서만 활성화된다. 기본 빌드에는 Cargo가 필요하지 않으며, 활성화된 경로에서 Rust 호출이나 출력 검증이 실패하면 C++ 구현으로 되돌아간다.
- Rust 보조 backend가 담당하는 일은 줄 분리, JSON 값 읽기, 차트 경로 검색, 곡 제목 정규화뿐이다. `BmsParser.cpp`의 BMS 헤더·채널·이벤트를 `Chart`로 조립하는 의미 분석, `SongSelectionModel`, Win32 입력과 렌더링은 계속 C++에 남아 있다. 이 parser helper 통합은 곡 선택 모델의 Rust 이전 단계와 별개다.
- `rust/song_selection`에는 1단계 ABI probe와 2단계 immutable snapshot API가 있다. 아직 곡 그룹화·선택 모델이나 플레이어 동작을 담당하지 않으며, 기존 parser helper crate와도 연결되지 않는다.

## 이전 원칙

1. **처음에는 모델만 Rust로 옮긴다.** Win32/GDI 화면과 키 입력은 계속 C++에서 처리한다. UI 프레임워크 교체는 모델 이전과 별도 결정으로 둔다.
2. **단계마다 기본 경로는 C++로 유지한다.** Rust 경로는 명시적으로 켜야 하며, 기본 빌드와 기존 플레이어의 동작을 바꾸지 않는다.
3. **동작을 먼저 고정하고 포팅한다.** 그룹 분리·병합, 정렬, 선택 유지, 변형 순환 등 현재 결과를 테스트 기준으로 기록한다.
4. **양쪽 언어의 메모리 소유자를 명확히 한다.** C++ `Chart` 객체나 `std::wstring` 내부 포인터를 Rust에 넘기지 않는다. Rust가 소유한 메모리는 Rust API가 해제하고, C++가 소유한 메모리는 C++가 해제한다.
5. **한 경로에서 선택 상태의 권위자는 하나뿐이다.** 비교용 shadow 실행은 테스트에서만 한다. 실제 앱에서 C++와 Rust가 각각 선택 상태를 보유해 동기화하는 구조는 만들지 않는다.
6. **Rust의 `unsafe`는 FFI 어댑터의 좁은 영역에만 둔다.** 가능한 한 나머지 모델은 safe Rust로 작성한다.

## 목표 구조

```text
BMS 파일 / C++ Chart 목록
          │  C++가 소유하는 값의 스냅샷
          ▼
     좁은 C ABI 경계
          ▼
Rust 곡 선택 모델
  그룹 순서 · 정렬 · 선택 · 채보 변형
          │  인덱스와 조회 결과
          ▼
C++ Win32 입력 · GDI 화면 · 미리 듣기 · 플레이어
```

Rust 곡 선택 모델은 차트 파일을 다시 해석하거나 미리 듣기 자원을 소유하지 않는다. 현재 활성 체크아웃에서 C++ `BmsParser`가 만든 차트 목록을 입력으로 사용한다. 기존 별도 Rust parser-helper 실험을 다시 활성화하더라도, 선택 모델은 parser 내부 자료형에 연결하지 않고 최종 C++ `Chart`의 안정된 요약 정보를 받는다. C++의 차트 목록이 재검색·재구성되면 새 스냅샷을 Rust 선택 모델에 전달하고, 그 이전 스냅샷에서 얻은 차트 인덱스는 폐기한다.

## 단계별 로드맵

### 0단계 — 기존 동작 계약과 기준선 작성

**목표:** 이전 전에 무엇을 보존해야 하는지 확정한다.

- `SongSelectionModel`의 public 동작과 `Main.cpp` 호출 흐름을 목록화한다.
- 곡 그룹 기준은 현재 폴더 정체성, 제목·작곡가·키 모드 처리 결과를 유지한다.
- 채보 변형 정렬에서 플레이 가능 여부, 숫자 레벨, 자막, 경로 순서를 유지한다.
- 제목 정렬의 영문 대소문자 처리 및 한국어·일본어 로캘 비교 결과를 보존한다. Rust의 기본 문자열 비교로 임의 대체하지 않는다.
- 정렬 후 현재 선택 곡 유지, 빈 목록, 중복 제목, 잘못된 인덱스, 채보가 하나뿐인 그룹과 변형 순환 경계를 기록한다.
- 기존 C++ 동작을 고정하는 회귀 테스트를 추가한다. 현 `SongGroupingTests`가 다루는 제목 정규화만으로 `SongSelectionModel` 전체 동작 검증을 대신하지 않는다.

**완료 조건:** 포팅 전후 결과를 비교할 수 있는 테스트와 요구 동작 목록이 마련된다.

### 1단계 — 독립 Rust crate와 opt-in 빌드

**상태: 완료 (2026-10-25).**

**목표:** 플레이어 동작을 바꾸지 않고 Rust 빌드 경로만 추가한다.

- `rust/song_selection/`에 Rust 라이브러리 crate를 만든다.
- 초기에는 외부 crate 의존성을 추가하지 않는다. UI toolkit도 이 단계에서 도입하지 않는다.
- Windows 빌드는 C++ MSVC 툴체인과 맞는 `x86_64-pc-windows-msvc` Rust 타깃을 사용한다.
- CMake 옵션(예: `BMS_ENABLE_RUST_SONG_SELECTION`)을 추가하고 기본값은 `OFF`로 둔다.
- 옵션이 꺼졌을 때는 Cargo 설치 여부와 무관하게 기존 C++ 빌드가 그대로 동작하게 한다.
- Rust 라이브러리를 C++에서 호출할 형식은 정적 라이브러리 또는 프로젝트의 배포 방식에 맞는 형식으로 고른다. MSVC CRT, Debug/Release, 아키텍처와 링크 호환성을 실제 빌드로 확인한다.

**완료 조건:** 옵션을 켠 빌드에서 작은 Rust 함수와 C ABI 경계가 빌드되고, 옵션을 끈 기존 빌드에는 변화가 없다.

**구현 결과:** `rust/song_selection`에 외부 crate 의존성이 없는 `staticlib`/`rlib`을 추가했다. `BMS_ENABLE_RUST_SONG_SELECTION`은 기본값이 `OFF`이며, 켜면 Windows x64 MSVC용 Rust 정적 라이브러리와 C ABI smoke test를 별도 빌드한다. Rust 정적 라이브러리는 `+crt-static` 설정을 사용한다. Release에서 Rust 함수가 C++에서 실제로 링크·호출되는 것을 확인했고, Debug smoke target은 Rust 정적 라이브러리를 링크하지 않는다. 기본값 `OFF` 구성에서는 Cargo를 탐색하지 않고 기존 `BmsPlayer`가 빌드된다. 이 단계에서는 `SongSelectionModel`, `Main.cpp`, 화면 동작을 변경하지 않았다.

**검증:** opt-in OFF/ON Release 빌드, Rust ABI smoke test, Rust 단위 테스트, 기존 `BmsSongSelectionTests`를 모두 통과했다. `cargo fmt --check`도 통과했다.

### 2단계 — FFI 계약과 데이터 스냅샷

**상태: 완료 (2026-10-25).**

**목표:** 언어 사이 경계를 제한하고 소유권을 문서화한다.

- Rust 모델은 불투명 핸들로 생성·사용·파기한다. C++에서 Rust 내부 포인터를 보관하거나 해제하지 않는다.
- 입력 문자열은 UTF-8 바이트 포인터와 길이 쌍으로 전달하고 Rust가 필요한 동안 소유할 문자열은 복사한다. NUL 종료를 전제로 하지 않는다.
- 차트/그룹 식별자와 배열 길이는 `uint32_t` 또는 `uint64_t` 등 폭이 고정된 타입으로 명시한다. 언어별 `size_t`를 ABI 계약으로 사용하지 않는다.
- Rust가 C++ 버퍼에 결과를 채우거나 고정 크기 필드/조회 API를 사용한다. Rust 할당 메모리를 C++의 `free`/`delete`로 해제하는 API는 만들지 않는다.
- 재검색 시 증가하는 catalog generation을 전달해 이전 스냅샷의 인덱스가 새 목록에서 잘못 사용되지 않도록 한다.
- 모든 외부 입력의 포인터·길이·인덱스·용량을 검사한다. 오류는 상태 코드로 반환한다. C++ 예외나 Rust panic이 ABI 경계를 넘어가지 않게 한다.
- 초기 ABI에는 콜백, 비동기 작업, 스레드 간 참조 공유를 넣지 않는다.

**완료 조건:** 정상·빈 데이터·잘못된 인덱스·짧은 출력 버퍼·잘못된 UTF-8 입력에서 경계 계약이 정의되고 테스트된다.

**구현 결과:** [FFI 계약 문서](RustSongSelectionFfiContract.md)와 C 호환 헤더를 추가했다. UTF-8 포인터/바이트 길이 입력, 고정 폭 ID·인덱스·generation, Rust가 소유하는 불변 스냅샷 핸들, caller-owned 출력 버퍼 API와 상태 코드를 정의했다. Rust는 입력 문자열을 검증한 뒤 복사하고, 출력은 필요한 바이트 길이를 보고한 후 충분한 용량에서만 기록한다. 생성·조회·파기 진입점은 계약된 포인터 조건을 확인하고, Rust panic은 unwind 가능한 경우 상태 코드로 바꾼다. 이 API는 아직 기존 `SongSelectionModel` 또는 `Main.cpp`에서 사용하지 않는다.

**검증:** 실제 MSVC C++/Rust Release 링크 테스트에서 정상·빈 목록, generation/count, UTF-8 왕복과 입력 버퍼 재사용, 잘못된 UTF-8·중복 ID·잘못된 mode/playable·인덱스·null 포인터, 짧은 출력 버퍼의 무부분쓰기를 확인했다. x64 구조체 크기와 정렬을 Rust와 C++ 양쪽에서 검사했다. Rust 단위 테스트/format, opt-in ON Release 빌드와 기본 OFF 빌드의 기존 곡 선택 테스트도 통과했다.

### 3단계 — Rust 모델과 동작 동등성 (구현 완료)

**목표:** 기존 C++ 모델과 같은 입력에 같은 결과를 내는지 검증한다.

- Rust 타입으로 그룹·차트 요약 정보, 그룹 순서, 선택 항목, 변형 인덱스를 표현한다.
- C++에서 불변 스냅샷을 전달하고 C++ 모델과 Rust 모델의 그룹 정체성 및 인덱스 결과를 테스트에서 비교한다.
- 그룹화·정렬처럼 시스템 로캘에 민감한 규칙은 결과가 동등하다는 증거가 있기 전까지 기존 C++/Windows 함수를 기준 동작으로 둔다. 차이가 있으면 Rust 구현을 조정하거나 해당 규칙을 우선 C++에 남긴다.
- 실제 사용자 곡 파일은 테스트 입력으로 복사·수정하지 않는다. 저장소의 합성 fixture를 기본으로 하고, 실제 라이브러리 검증은 별도의 읽기 전용 절차로 한다.
- `rebuild`, `sort`, `toggleSort`, `selectGroup`, `clearSelection`, `selectedChartIndex`, `cycleSelectedVariant` 경계를 모두 다룬다.

**완료 조건:** 대표 회귀 입력에서 Rust 결과가 기준 동작과 일치하고, 테스트에서 Rust 모델 오류가 기본 플레이어 상태를 변경하지 않는다.

**구현 결과 (2026-10-25):** Rust 모델이 폴더 기준 그룹화, 변형/그룹 정렬, 선택 유지와 변형 순환을 소유한다. C++ `BmsSongSelectionTests`가 이 Rust 모델을 통하는 어댑터를 실행하며 기존 대표 동작을 검증한다. 제목 표준화, Windows 로캘 분류에 필요한 입력값, 정확한 숫자 레벨은 현재 C++에서 계산해 전달한다. 사용자 곡 폴더는 테스트에서 읽거나 수정하지 않는다.

### 4단계 — C++ 화면에 Rust 모델 연결 (구현 완료, UI 수동 검증 대기)

**목표:** 기존 UI를 유지한 채 Rust 모델을 실제 곡 선택 흐름에 연결한다.

- 빌드 옵션이 켜진 개발 빌드에서만 Rust 모델을 선택 상태의 권위자로 사용한다.
- 기존 ListView, `drawBrowseScreen`, 키보드 입력, 미리 듣기와 플레이 시작 호출은 C++에 둔다.
- `Main.cpp`의 직접 모델 접근을 얇은 C++ 어댑터로 모아 Rust API를 `Main.cpp` 여러 위치에서 직접 호출하지 않게 한다.
- Rust 초기화 또는 스냅샷 교체가 실패하면 현재 세션을 예측 불가능하게 계속하지 않는다. 안전한 오류 상태를 표시하고 C++ 기본 경로로 돌아가거나 곡 선택 화면을 유지한다.
- 개발 중 비교 모드는 테스트/진단에서만 켜고, 화면을 그리는 매 프레임마다 전체 목록을 복제하거나 Rust와 C++ 양쪽 선택 상태를 계속 동기화하지 않는다.

**완료 조건:** Rust 경로에서 곡 검색 후 선택, 정렬, 변형 변경, 미리 듣기, 플레이 진입, 결과/일시정지 후 복귀가 기존과 동일하게 동작한다. 기본 Release 구성에서 Rust를 사용하고, CMake 옵션으로 C++ 경로를 선택할 수 있다.

**구현 결과 (2026-10-25):** `SongSelectionRust.cpp` 어댑터를 `bms_song_selection`의 Release 구현으로 연결했다. `Main.cpp`와 Win32 화면은 기존 `SongSelectionModel` API를 계속 사용하며 Rust ABI를 직접 호출하지 않는다. 어댑터는 Rust 모델의 결과만 C++ `SongGroup` 표시값으로 복사하고 기존 미리 듣기 타이밍 공유를 적용한다. Rust rebuild가 실패하면 곡 그룹 목록을 비워 안전하게 실패한다. `BMS_ENABLE_RUST_SONG_SELECTION` 기본값은 `ON`이다. C++ Debug `/MTd`와 Rust 정적 라이브러리 `/MT`가 달라 Debug는 기존 C++ 구현을 사용하며, Rust ABI smoke 테스트도 Release에서만 실행한다.

### 5단계 — 안정성·성능 확인

**상태:** 사용자 수동 확인 후 다음 단계로 진행 (2026-10-25). 여러 해상도에서 정상 표시됨을 사용자가 확인했다. 대형 목록의 정량 성능·장시간 메모리 비교는 측정 완료로 주장하지 않으며 후속 확인 항목으로 보관한다.

**목표:** 실제 목록 규모와 반복 사용에서도 안정성을 확인한다.

- 소형·대형 곡 목록과 여러 번의 목록 재구성에서 메모리 사용량이 안정적으로 유지되는지 확인한다.
- 선택 이동 및 재정렬의 UI 반응 시간, 초기 목록 구성 시간, 메모리 사용량을 C++ 기준선과 같은 환경에서 비교한다.
- Korean/Japanese/English 제목, 전각 문자, 경로가 유사한 곡, 난이도 표기 없는 차트와 중복 차트를 검증한다.
- Windows 앱의 키보드·마우스 포커스, DPI/창 크기 변경, 실패 복구와 종료 경로를 수동 점검한다.
- 모델 갱신마다 Rust 핸들과 버퍼가 반복 생성되지 않는지 확인한다. `Rc`/`RefCell` 순환 소유를 피하고, FFI `unsafe` 사용처를 재검토한다.
- C++ 모델은 긴급 복귀 경로로 보존한다. 문제가 나면 `BMS_ENABLE_RUST_SONG_SELECTION=OFF`로 선택할 수 있어야 한다.

**완료 조건:** 동작 회귀가 없고, 측정 결과가 기준선보다 유의하게 나빠지지 않으며, 반복 재구성/종료 후 자원 수명 문제가 없음을 확인한다. 기본 Release 경로는 사용자 요청에 따라 Rust로 먼저 전환했다. 성능 측정, 대형 목록 반복 재검색, 실제 화면 입력 흐름 점검은 남아 있다.

### 6단계 — RmlUi 곡 목록 표시 도입

모델을 Rust로 옮겼다고 화면도 Rust로 옮길 필요는 없다. 먼저 C++ Win32/GDI 화면과 Rust 모델 조합을 안정화한다. 이후 시각 디자인 개선이 필요하면 Rust UI toolkit 도입을 별도 실험으로 검토하고, 렌더러·입력 포커스·창 수명·프레임 타이밍을 독립적으로 평가한다. RmlUi를 선택한다면 C++ 라이브러리이므로 Rust FFI와 UI renderer까지 동시에 바꾸는 방안은 피한다.

**구현 결과:** RmlUi 6.3/FreeType 2.15.0을 고정된 Git submodule로 도입했다. C++ ListView의 실제 보이는 행만 RML/RCSS로 표시하고 입력·스크롤은 ListView, 선택 상태는 Rust 모델이 계속 관리한다. 별도 DX11 텍스처의 결과를 변경 시에만 읽어 GDI 출력과 연결하며 동일 화면은 비트맵 캐시로 그린다. 디자인 파일과 빌드·수명·검증 범위는 [도입 문서](RmlUiSongListIntegration.md)에 기록했다.

## 이전 성공 기준

- 기존 기본 빌드와 플레이 흐름은 Rust 실험 옵션 없이 그대로 유지된다.
- Rust 모델은 소유권·수명 관리가 명확하고 FFI 외부에 불필요한 `unsafe`가 없다.
- 그룹화, 정렬, 선택 유지와 변형 순환의 결과가 기존 계약과 일치한다.
- C++/Rust가 소유하는 문자열·배열·핸들의 생성과 해제 주체가 문서 및 코드에서 명확하다.
- Rust 도입으로 인한 빌드 복잡도와 실행 성능이 측정되며, 회귀 시 C++ 경로로 빠르게 복귀할 수 있다.

## 현재 상태와 다음 확인

Rust 선택 모델에 이어 RmlUi 곡 목록 표시를 도입했다. 다음 수동 확인은 새 목록에서 클릭·스크롤과 행 위치 일치, 난이도 변경, 설정창 및 플레이/결과/QUIT 복귀다. 사용자 곡 폴더를 자동 테스트에서 읽거나 수정하지 않았다. 기존 `BmsUiTests`의 startup timeout은 이전 Rust ON/OFF 두 구성에서 모두 발생했던 별도 문제로 남아 있다.
