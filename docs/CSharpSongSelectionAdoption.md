# C# 곡 선택·설정 화면 부분 도입안

## 목표와 현재 구조

곡 선택·설정 화면의 디자인과 유지보수성을 높이면서, 재생 중 입력·판정·오디오가 GC 정지의 영향을 받지 않도록 C#을 프런트엔드로 부분 도입한다. 인터프리터 언어는 사용하지 않는다. C#은 .NET에서 JIT 또는 선택적인 AOT 방식으로 실행되며 GC를 사용한다. GC 정지를 재생 엔진과 분리하는 핵심은 화면 프로그램과 플레이어를 별도 프로세스로 두는 것이다.

현재 `src/Main.cpp`는 곡 목록, 설정 창, 곡 스캔 시작, 곡 재생, 입력·판정과 렌더링 진입점을 한 Windows 실행 파일에 담고 있다. `scanFolder()`는 곡 폴더 가져오기와 분석을 백그라운드 스레드에서 실행하고, `settingsProc()`는 Win32 컨트롤 및 설정 처리를 맡는다. 따라서 화면만 C#으로 바꾸려면 먼저 C++ 실행 파일에 “곡 선택 화면 없이 지정된 곡을 재생하는 진입점”을 마련해야 한다.

## 권장 구성

```text
C# WPF 프런트엔드
  곡 목록 · 검색 · 정렬 · 설정 · 기록 표시
       │ 버전이 있는 JSON 파일과 필요할 때만 IPC
       ├──────── Rust 라이브러리 (추후)
       │          채보 해석 · 곡 메타데이터 조회
       └──────── C++ 플레이어 프로세스 실행
                  WASAPI 오디오 · 입력 · 판정 · 플레이 렌더링
```

C#은 목록 행, 곡 정보 패널, 설정 화면처럼 사용자 조작과 디자인이 중심인 영역을 담당한다. C++은 오디오 시계, 오디오 버퍼 공급, 키 입력 판정, 플레이 중 프레임 제어와 기존 Direct3D/Direct2D 출력 경로를 유지한다. 픽셀 단위 효과를 GPU로 옮길 필요가 생기면 HLSL을 별도로 검토한다.

곡 선택 화면과 C++ 플레이어는 별도 프로세스로 실행한다. 선택 시 C#이 채보 경로와 적용할 설정을 플레이어에 전달한다. 플레이어는 준비·종료·결과 같은 드문 상태만 전달한다. 매 프레임 데이터나 입력 이벤트를 C#으로 보내지 않는다. 이 구조에서는 C# GC가 C# 프로세스의 UI 응답을 늦출 수는 있어도, 플레이어 프로세스의 오디오·판정 스레드를 직접 정지시키지는 않는다. 두 프로세스가 CPU·메모리·디스크·GPU를 공유하므로 자원 경쟁은 측정해야 한다.

## C# 화면 구성

WPF와 XAML을 사용하고 MVVM으로 화면을 나눈다.

- **View/XAML:** 목록, 검색 상자, 정렬 메뉴, 상세 정보, 설정 탭과 스타일을 선언한다.
- **ViewModel:** 곡 목록, 선택된 채보, 로딩 상태, 검색·정렬 명령, 설정 화면 상태를 관리한다.
- **Model:** 화면에 필요한 데이터만 담는 `ChartSummary`, `SongGroup`, `PlayerSettings` 같은 단순 자료형이다.

C#의 곡 항목은 기존 C++ `bms::Chart` 전체를 복제하지 않는다. 목록과 상세 패널에 필요한 제목·아티스트·레벨·BPM·모드·실행 가능 여부·차단 사유·파일 경로만 전달한다. 긴 목록은 가상화하고, 폴더 탐색과 메타데이터 분석은 비동기 처리한다. 미리보기 이미지와 썸네일은 화면에 필요한 때 읽고, 캐시에는 개수나 용량 상한을 둔다. 이벤트 구독과 타이머는 화면이 닫힐 때 해제한다.

기존 키보드 사용 흐름도 유지한다. 위·아래 방향키로 곡을 이동하고, 좌·우 방향키로 같은 곡의 난이도를 바꾸며, Enter로 재생한다. 기존에 제공하는 숨겨진 채보 보기, 로딩 취소, 진행률, 미리보기, 마지막 라이브러리 복원도 기능 목록으로 관리해 이전 중 빠뜨리지 않는다.

## C++·C#·Rust 사이의 데이터 경계

언어 간에는 내부 클래스와 컨테이너를 직접 공유하지 않는다. 안정적인 경계 데이터로 UTF-8 JSON을 사용한다. 예를 들어 목록 응답은 다음과 같은 버전 필드와 곡 요약 배열을 가진다.

```json
{
  "schemaVersion": 1,
  "charts": [
    {
      "path": "Songs/example/chart.bms",
      "title": "Example",
      "artist": "Artist",
      "level": "12",
      "mode": "SevenKey",
      "playable": true,
      "blockReason": ""
    }
  ]
}
```

초기 단계에서는 기존 C++ 파서와 곡 라이브러리의 판정 기준을 재사용하는 것이 안전하다. C++ 실행 파일에 목록 조회용 명령행 모드를 추가해 UTF-8 JSON 카탈로그를 출력하고, 별도 `--play <chart-path>` 모드로 선택된 곡을 재생하도록 점진적으로 분리한다. 진행 중 취소와 오류 상태 전달은 표준 출력의 JSON 한 줄 메시지 또는 named pipe 중 하나로 명시한다. 표준 출력은 프로토콜에만 사용하고 진단 로그는 표준 오류로 보낸다.

이후 채보 파서를 Rust로 옮기면 Rust DLL이 C ABI의 명시적인 함수만 내보내거나, 독립 도구가 같은 JSON 계약을 생성하도록 한다. C#에는 Rust 구조체나 C++ STL 타입을 노출하지 않는다. DLL 방식은 버퍼 인코딩, 오류 반환, 메모리 해제 주체를 계약에 포함한다. 한 단계에서 파서 언어와 화면 언어를 동시에 바꾸지 않는다.

## 설정과 기록의 소유권

설정 저장 위치와 값의 의미를 한 군데에서 관리한다. C#이 설정 화면과 저장을 소유하고, 플레이어 시작 시 버전이 명시된 설정 파일 경로를 전달하는 방식을 권장한다. 현재 `Main.cpp`는 `%APPDATA%\\BmsPlayer\\keybindings.ini`와 진단용 INI 경로를 사용하므로, 전환 기간에는 기존 INI를 읽는 호환 계층을 두거나 마이그레이션한다. 설정을 새 JSON으로 옮긴다면 값 범위, 기본값, 기존 키 매핑과 사용자 설정 보존 규칙을 먼저 정의한다.

플레이 중 바꾼 설정을 즉시 적용해야 한다면 named pipe로 설정 변경 명령을 보낸다. C++이 적용 결과를 회신하고, 저장은 단일 소유자가 맡는다. 전체 설정을 빈번하게 동기화하거나 양쪽 프로그램이 같은 파일을 동시에 덮어쓰지 않는다. 플레이 기록도 한쪽만 쓰도록 정한다.

## 단계별 이전

1. **계약과 기존 동작 기록:** 현재 곡 목록 필드, 정렬·그룹·난이도 이동, 숨김 채보, 설정 항목, 설정 파일 호환, 취소·오류 동작을 목록화한다. JSON 스키마 버전과 샘플 응답을 정한다.
2. **C++ 실행 모드 분리:** 기존 기본 실행은 그대로 두고, 카탈로그 출력 모드와 선택 곡 직접 재생 모드를 추가할 수 있도록 진입점을 나눈다. 이 단계에서 기존 파싱·재생 결과를 기준 동작으로 삼는다.
3. **C# 목록 프로토타입:** WPF 곡 목록과 상세 화면을 만들고 C++ 카탈로그를 읽는다. 검색·정렬·선택·난이도 이동·숨김 채보를 확인한다. 초기에 C++ 기존 화면도 유지해 기능을 비교할 수 있게 한다.
4. **선택 곡 실행 연결:** C#에서 C++ 플레이어를 시작해 선택 곡을 실행하고, 종료 코드 및 결과를 돌려받는다. 이때 재생 중 C#과의 프레임별 통신이 없는지 확인한다.
5. **설정·기록 이전:** 설정 화면과 저장을 항목별로 옮기고 기존 INI를 보존하거나 변환한다. 라이브러리 복사, 미리보기, 화면 모드 등 플레이어와 밀접한 설정은 적용 시점과 소유자를 따로 확인한다.
6. **Rust 파서 검토:** C# 화면과 C++ 재생 경계가 안정된 다음 파서 모듈을 옮긴다. 기존 파서와 같은 채보를 읽어 제목·레벨·모드·노트 시각·자산 경로·실행 가능 여부가 일치하는지 비교한다.

초기 릴리스에서는 C++ 기존 화면을 폴백으로 남기고, 새 프런트엔드와 플레이어를 별도 실행 파일로 제공하는 것이 안전하다. C# 화면의 기능·설정 호환·곡별 분석 결과를 확인한 뒤 기존 Win32 곡 선택 화면의 사용 종료를 결정한다.

## GC 정지와 메모리 누수 대응

프로세스를 나누면 GC 정지가 재생 프로세스를 직접 멈추지 않게 할 수 있다. C# 프런트엔드에서도 목록 갱신 시 임시 객체를 과도하게 만들지 않고, 큰 이미지·배열을 반복 생성하지 않으며, 썸네일 캐시를 제한한다. GC 저지연 모드는 필요 시 짧은 구간에만 검토한다. .NET의 저지연 설정은 GC를 완전히 끄지 않으며 메모리 사용과 회수 시점의 trade-off가 있다. 플레이어 실행 전체에 No-GC 구간을 적용하는 방식은 메모리 예산을 넘으면 보장되지 않으므로 기본안으로 삼지 않는다.

GC는 관리 힙 객체를 회수하지만 파일 핸들, COM 객체, GPU 텍스처와 오디오 장치를 자동으로 적시에 닫아 주지는 않는다. C#에서는 `IDisposable`/`SafeHandle`, C++에서는 RAII와 COM `ComPtr`로 외부 자원의 해제 시점을 명시한다. Rust는 일반 소유권으로 수명을 관리하되 참조 카운트 순환과 FFI 경계를 주의한다. 따라서 GC 사용과 별개로 자원 소유자를 한 곳으로 정해야 한다.

## 완료 기준

- 기존 곡 목록의 그룹·정렬·난이도 선택과 실행 가능 표시가 유지된다.
- C# 화면에서 곡을 고르면 해당 차트가 C++ 플레이어에서 재생된다.
- 재생 중 오디오·판정 처리는 C# 프로세스 응답이나 GC에 의존하지 않는다.
- 기존 사용자 설정과 기록이 보존되거나 검토 가능한 방식으로 변환된다.
- 반복해서 곡을 불러오고 화면을 열고 닫아도 관리 힙, 네이티브 자원, GPU 메모리가 계속 증가하지 않는다.
- 곡 로딩 취소·오류·플레이어 종료가 화면에 일관되게 반영된다.
