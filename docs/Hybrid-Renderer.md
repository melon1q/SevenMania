# CPU/GPU 하이브리드 렌더링 실험

브랜치: `codex/hybrid-renderer`. `main`에 병합하지 않았다.

```powershell
./tools/Build-PerformanceExperiment.ps1 -Variant Hybrid
```

`build/Release/BmsPlayer-Hybrid.exe`를 실행하고 그래픽 설정의 **CPU + GPU 하이브리드 사용**을 체크한다.
기존 실행파일과 같은 Songs, Assets, 설정을 사용한다. 비교 시 하나씩 실행한다.
기존 `BmsPlayer-Optimized.exe`와 `BmsPlayer.exe`는 유지했다.
새 경로는 CMake `BMS_HYBRID_RENDERER=ON`일 때만 활성화되며 기본값은 OFF다.
mimalloc·oneTBB는 Hybrid에서도 ON이다. 체크 해제 시 기존 CPU 렌더러로 돌아간다.

## 적용한 내용

- CPU: 오디오·판정·노트, 키 빔, 건반, 영상 디코드/이미지 준비를 담당한다.
- GPU: 변경될 때만 업로드하는 배경 텍스처, BGA 밝기/레인 덮개, 캐시된 텍스트/스플래시,
  CPU가 그린 작은 영역의 최종 합성을 담당한다.
- 전체 화면 DIB를 매 프레임 업로드하는 대신 기어와 작은 정보 영역만 전송한다.
  배경 텍스처는 BGA 세대가 바뀔 때만 갱신한다. 배경 밝기 처리를 CPU 전체 화면 루프에서 GPU 합성으로 옮겼다.
- VSync에서는 GPU 제출 준비 신호를 CPU 기어/HUD를 그리기 전에 확인한다. 아직 새 화면을 제출할 수 없으면
  CPU 그리기와 GPU 업로드/합성을 건너뛰고 입력·판정 루프는 기존 FPS 설정대로 계속 실행한다.
  숫자 제한/무제한은 CPU 그리기를 독립적으로 수행하고, GPU가 바쁠 때 업로드/합성만 생략한다.
- 프레임 제한의 `VSync` 선택 시에만 `Present(1, DXGI_PRESENT_DO_NOT_WAIT)`로 갱신에 동기화한다.
  숫자 제한/무제한은 `Present(0, DXGI_PRESENT_DO_NOT_WAIT)`를 사용한다.
  별도 주사율/+50FPS 타이머는 제거했다. 준비 신호를 예약해 그리기와 제출 단계에서 두 번 기다리지 않는다.
- 건반 전체는 눌림 상태/스킨/회전각이 달라졌을 때만 CPU에서 다시 그린다.
  스크래치 각도는 0.5도 단위로 캐시한다. 키 입력 상태는 즉시 반영한다.
- 기존 텍스트 스프라이트 캐시와 GPU 배율 애니메이션은 유지한다. 숫자별 글리프 아틀라스는 추가하지 않았다.
- BGA 밝기 0%에서는 영상 갱신 요청을 중단한다. 다시 켤 때 현재 음악 시각으로 갱신한다.
- 일시정지 메뉴, CPU 폴백, 화면 크기 변경, 연습 HUD, 키 가이드, 레인 투명도를 유지한다.

표시되는 `FPS`는 화면 그리기 횟수이며, `OUTPUT`은 성공한 GPU 제출률이다.
실제로 모니터가 표시한 프레임 수를 직접 측정하는 값은 아니다. 제출 전 CPU 그리기도 생략하므로
VSync에서 하이브리드의 FPS는 보통 출력 주사율 근처다. 입력·판정 업데이트 횟수를 뜻하지 않는다.

## 프레임 제한 선택

요약/그래픽 탭에서 60, 144, 240, 400 FPS, 무제한(최대 1500 FPS), VSync를 선택한다.
기존 설정의 `FPS=0`은 무제한을 유지하며 새로 1500FPS 상한을 적용한다. `FPS=-1`이 VSync다.
VSync는 선택한 경우에만 켜진다. GPU 렌더러는 동기화 간격 1을 사용하고, CPU 폴백은
`GdiFlush` 후 `DwmFlush`로 화면 합성을 기다린다. CPU 폴백에서는 이 대기가 입력 처리에도 영향을 줄 수 있다.
그 외 선택에는 수직 동기화 대기를 요청하지 않는다. 창 모드에서는 Windows 합성기가 실제 표시 주기를 결정할 수 있다.
무제한의 1500 상한은 CPU 렌더링/업데이트 루프에 적용하며 하이브리드의 GPU 제출 횟수는 이보다 낮을 수 있다.
설정은 즉시 저장하고 프레임 타이머에도 즉시 반영한다. VSync 입력/업데이트 루프 역시 1500Hz 이내로 동작한다.

## 무제한 성능 회귀 수정

무제한에도 GPU 준비 전 CPU 그리기 생략을 적용하면서 표시 FPS가 GPU 제출 횟수에 묶였다.
또한 1500 상한을 고정 시각표로 처리해 프레임 처리/타이머 지연으로 기한을 넘기면 다음 슬롯까지 기다렸다.
숫자 제한/VSync의 기존 시각표는 유지하고, 무제한만 시작 간격의 최소값(약 0.667ms)으로 상한을 적용한다.
처리 자체가 이보다 오래 걸렸으면 추가로 대기하지 않는다. 짧은 대기는 입력 메시지를 계속 처리하며
`YieldProcessor`로 폴링하므로 무제한에서 CPU 한 코어 사용량이 늘 수 있다.

동일 Creamy/240Hz/1920×1080 설정의 8초 비교에서 종료 직전 표시 FPS는 240 → 1365,
GPU 제출은 1900 → 3584회(약 238 → 448회/초)였다. CPU 루프의 31~37초 평균은 1158 → 1422회/초,
성공 제출 간격 추정치의 99백분위는 7.726 → 4.915ms였다. 출력 횟수는 실제 스캔아웃 횟수와 다르다.
원본은 `build-hybrid-results/unlimited-regression-*.csv`에 남겼다.
프레임 타이머 단독 테스트에서도 무제한의 상한뿐 아니라 처리율 하한과 이미 예산을 넘긴 프레임의 추가 대기 방지를 검증한다.

## 출력 간격 안정화 후속 실험 (VSync 경로 측정)

별도 +50FPS 제한은 디스플레이 갱신과 위상이 달라져 준비된 제출 시점을 놓칠 수 있었다.
제한만 제거한 실험은 GPU 업로드를 늘렸고, 동기화만 적용한 실험은 CPU의 버려지는 그리기 비용이 남았다.
준비 신호 확인을 CPU 그리기 앞으로 옮기고, 동기화된 비차단 제출을 함께 사용했다.
현재는 이 동기화 경로를 프레임 제한의 VSync를 선택했을 때 사용한다.

동일 240Hz PC/설정의 8초 자동 재생에서 Creamy는 1,918회, energy trixxx는 1,917회 제출했고
두 곡 모두 종료 직전 FPS는 240이었다. 31~37초 구간 제출 간격의 중앙값은 각각 약 4.166ms,
95백분위는 4.353ms/4.312ms였다. 전체 측정의 주화면 업로드는 각각 약 7,158MiB/7,258MiB였다.
`build-hybrid-results/pacing-*.csv`에 원본을 남겼다.

CSV의 제출 간격은 성공한 프레임의 CPU 루프 시작 시각으로 추정한 값이며 실제 스캔아웃 간격이 아니다.
최대 공백은 각각 약 41.65ms/12.62ms로 드문 긴 지연까지 사라졌다고 단정할 수 없다.
진단 CSV 기록과 OS 스케줄링 비용도 포함되며, 실제 배포 실행파일은 CSV를 기록하지 않는다.
GPU 테스트는 자동 리셋 준비 신호의 예약/소비와 연속 준비 시 타이머에 막히지 않는 것도 확인한다.

## 최초 하이브리드 실험의 검증 범위와 남은 비용

동일 PC/설정(1920×1080, 배속 6, 버퍼 32, BGA 20%, FPS 무제한)에서 기존 GPU 릴리즈와
하이브리드 릴리즈를 번갈아 8초 재생한 참고 측정이다. mimalloc·oneTBB ON, Tracy OFF이며,
처리 시간/FPS는 시크 직후를 제외한 31~37초 CSV에서 계산했다.

| 항목 | 기존 GPU | Hybrid |
| --- | ---: | ---: |
| Creamy 처리 루프 FPS | 1,052 | 3,002 |
| Creamy 평균 CPU 프레임 | 0.930 ms | 0.321 ms |
| Creamy CPU 프레임 p99 | 2.128 ms | 0.999 ms |
| Creamy 건반 CPU 시간 | 0.119 ms | 0.029 ms |
| Creamy 주화면 전송량(8초) | 66,778 MiB | 7,175 MiB |
| Creamy GPU 제출 프레임(8초) | 1,925 | 1,921 |
| Creamy 수집된 GPU 타임스탬프 구간 합 | 7,228 ms | 1,078 ms |
| energy trixxx 처리 루프 FPS | 1,023 | 2,979 |
| energy trixxx 평균 CPU 프레임 | 0.947 ms | 0.321 ms |
| energy trixxx 주화면 전송량(8초) | 65,702 MiB | 7,253 MiB |
| energy trixxx GPU 제출 프레임(8초) | 1,927 | 1,915 |
| energy trixxx 수집된 GPU 타임스탬프 구간 합 | 7,148 ms | 1,171 ms |

주화면 전송량은 약 89% 감소했고, 화면 제출률은 양쪽 모두 약 240Hz였다.
기존 GPU 경로는 화면에 제출하지 못하는 프레임도 GPU에서 그렸지만, Hybrid는 이를 생략한다.
높아진 처리 루프 FPS가 초당 3,000장의 화면을 표시한다는 뜻은 아니다.
GPU 타임스탬프 구간은 하드웨어 명령 사이의 CPU 제출 간격도 포함할 수 있고 표본이 누락될 수 있으므로
전체 GPU 엔진 사용률이나 작업관리자 수치로 환산하지 않는다. 전송량 카운터는 주화면/Hybrid CPU 영역이며
기존 경로의 별도 건반·텍스트 텍스처 전송은 포함하지 않는다.
원본 CSV/콘솔 결과는 Git에서 제외한 `build-hybrid-results`에 보관한다.

GPU 픽셀 테스트에서 배경 세대 재사용/변경, 밝기, 레인 덮개, CPU 영역 이동으로 인한 잔상 방지,
큐가 찼을 때 업로드 생략을 확인한다. 화면 테스트는 CPU 노트 경로, 건반 캐시의 픽셀 일치/눌림/스킨 갱신을 검증한다.
Hybrid GPU/화면/오디오 테스트 3개와 기존 경로 GPU/화면 테스트 2개를 통과했다.

영상 디코드·확대와 이미지의 최초 준비는 CPU에서 계속 한다. 레인 투명도를 높이면 CPU 영역에서도
배경 밝기를 적용하므로 불투명 레인보다 CPU 비용이 커진다. GPU 전체 파이프라인 교체는 하지 않았다.
GPU 전송량과 타임스탬프 구간 합계를 측정하며, 이 값은 작업관리자의 전체 GPU 사용률과 같지 않다.
실제 GPU 부하/소비전력은 GPU 모델·드라이버·주사율·화면 모드별로 사용자가 확인해야 한다.
